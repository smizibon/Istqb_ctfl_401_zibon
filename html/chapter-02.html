2.1 How the SDLC shapes testing

K2

How you build software decides when you test; DevOps automates it; shift-left pulls it earlier.

In plain words: the way a team builds software sets when testing happens — and good teams start it earlier.

Core idea (2.1.1): every SDLC model — sequential (waterfall, V-model), iterative/incremental (spiral, RUP), or agile (Scrum, Kanban, XP) — changes when and how you test:

  • Sequential: test levels follow phases; detailed test preparation can start early from documentation; test execution happens late.
  • Iterative/agile: regression testing grows in importance each iteration (the system keeps changing); lightweight, communicate-often test documentation; development and testing run concurrently in the same iteration; continuous feedback.
  • In every model the test process activities (Ch. 1) still happen — only their timing, formality, and frequency change.

DevOps (2.1.2)

🧠 Understand — DevOps benefit/challenge pairs DevOps = development + operations collaborating, with automation of the deployment pipeline.
Benefits: fast feedback on quality and usability (CI → automated builds and tests on every commit), shorter time-to-market, defects found and fixed quickly, automated regression suites make frequent releases safe.
Challenges: the pipeline itself must be maintained and automated (test automation is an ongoing investment, not a one-off); team needs new skills; unmanaged feedback loops drown teams in automated failures.

Shift-left (2.1.3)

📖 Memorise — both halves of shift-left Move test activities earlier in the lifecycle — and it is more than "start testing sooner": (a) testing work products earlier (reviews, static analysis, early test design) and (b) testers involved from the start in requirements/user stories, improving testability and preventing defects. Both halves are the correct meaning.
⚠️ TrapShift-left described only as "starting test execution earlier" is incomplete — the exam wants early work-product testing + early tester involvement.

Retrospectives & process improvement (2.1.4)

After each iteration/release, the team reflects: what went well, what to improve — including test process improvement (better automation, improved defect prevention, revised estimation). Lessons feed the next cycle. Exam scenario: "team meets after sprint to improve testing" → retrospective.

Sequential বনাম agile testing, DevOps-এর benefit/challenge জোড়া, আর shift-left মানে আগেভাগে work product টেস্ট করা + শুরু থেকেই tester-দের যুক্ত করা।

মূল আইডিয়া (2.1.1): প্রতিটি SDLC মডেল — sequential (waterfall, V-model), iterative/incremental (spiral, RUP), বা agile (Scrum, Kanban, XP) — বদলে দেয় আপনি কখন আর কীভাবে টেস্ট করবেন:

  • Sequential: test level গুলো phase-এর পরে phase ধরে চলে; ডকুমেন্টেশন থেকে বিস্তারিত test preparation শুরু হতে পারে; test execution হয় অনেক পরে।
  • Iterative/agile: প্রতিটি iteration-এ regression testing-এর গুরুত্ব বাড়তে থাকে (সিস্টেমটা ক্রমাগত বদলায়); হালকা, ঘন ঘন যোগাযোগ-ভিত্তিক test documentation; একই iteration-এর ভেতরে development আর testing একসাথে চলে; continuous feedback।
  • যে মডেলেই হোক, test process-এর activity গুলো (Ch. 1) তবুও ঘটে — শুধু সেগুলোর সময়, formality আর frequency বদলায়।

DevOps (2.1.2)

🧠 Understand — DevOps benefit/challenge জোড়া DevOps মানে development + operations একসাথে কাজ করা, সঙ্গে deployment pipeline-এর automation।
Benefits: quality আর usability নিয়ে দ্রুত feedback (CI → প্রতিটি commit-এ automated build ও test), time-to-market ছোট হয়, defect দ্রুত ধরা পড়ে ও ঠিক হয়, automated regression suite-গুলো ঘন ঘন release-কে নিরাপদ করে।
Challenges: pipeline নিজেই maintain আর automate করতে হয় (test automation একটা চলমান investment, এককালীন নয়); দলকে নতুন skill শিখতে হয়; নিয়ন্ত্রণ ছাড়া feedback loop দলকে automated failure-এর ভেতরে ডুবিয়ে দেয়।

Shift-left (2.1.3)

📖 Memorise — shift-left-এর দুই অর্ধেক Test activity গুলো lifecycle-এ আরও আগে সরিয়ে আনা — আর এটা শুধু "আগে টেস্ট শুরু করা" নয়: (a) work product আগেভাগে টেস্ট করা (review, static analysis, আগেভাগে test design) এবং (b) requirements/user story থেকেই tester-দের যুক্ত করা, যাতে testability বাড়ে আর defect প্রতিরোধ হয়। দুই অর্ধেক মিলেই সঠিক অর্থ।
⚠️ TrapShift-left-কে শুধু "starting test execution earlier" বলা অসম্পূর্ণ — পরীক্ষায় চাই আগেভাগে work-product testing + আগেভাগে tester involvement।

Retrospectives & process improvement (2.1.4)

প্রতিটি iteration/release-এর পরে দল প্রতিফলিত করে: কী ভালো হলো, কী উন্নত করা যায় — এর মধ্যে test process improvement-ও পড়ে (ভালো automation, ভালো defect prevention, সংশোধিত estimation)। শেখা শিক্ষা পরের cycle-এ খাওয়ানো হয়। Exam scenario: "team meets after sprint to improve testing" → retrospective।

2.2 Test levels and test types — the chapter's core

K2

Levels say how big a thing you test; types say what kind of test you run — and they mix freely.

In plain words: level = how much of the system you test; type = what question the test asks. Mix and match.

Level = scope · Type = nature — two independent axes; ANY type runs at ANY level.

The four test levels (2.2.1)

Component
one unit in isolation (stubs/mocks) · developers→ Component integration
interfaces & interactions between components · developers→ System
whole-system behaviour end-to-end · independent testers→ Acceptance
validation: meets user/business needs · users/ops
📖 Memorise — the four levels in detail
LevelScope / test basisWho & notes
Component (unit)Single components in isolation; code, design, spec of the componentDevelopers; mock objects/stubs to isolate
Component integrationInteractions & interfaces between components; architecture/design docsDevelopers primarily
SystemWhole system's behaviour & capabilities, end-to-end; requirements/spec, use cases, risk analysisIndependent test team; functional + non-functional; also behaviour no single requirement describes
AcceptanceValidation — meets user needs/business goals?; often the entry criterion for releaseUsers/customers, ops, support; forms: user acceptance, operational, contractual/regulatory, alpha (developer's site), beta (user's site)
⚠️ Classic exam item: "verifying interaction between modules" = component integration; "checking the delivered system meets business needs with real users" = acceptance.

The four test types (2.2.2)

📖 Memorise — the four types
TypeTargetExamples
FunctionalWhat the system does — functions it performsSearch, payment, interest calculation; possible at all levels (e.g., component tests of a function's behaviour)
Non-functionalHow well it behaves — quality characteristicsPerformance, usability, security, reliability; also all levels
Black-boxBehaviour from outside, based on specifications — no knowledge of internalsSpec-based test derivation
White-boxInternal structure of the system/code drives the testsStatement/branch coverage of code
Key idea: a test type can be applied at every test level (this surprises people). Black-box vs white-box is about the basis of test derivation (spec vs structure) — not about "who runs it".

Confirmation vs regression testing (2.2.3)

📖 Memorise — near-guaranteed exam question
Confirmation (re-testing)Regression testing
PurposeVerify a specific defect is really fixed — and the fix caused no adverse effectsVerify a change broke nothing else
Runs onThe fixed defect's test (+ anything needed to re-run it)Affected areas + previously working areas at risk
WhenAfter the fix is deliveredAfter any change: fixes, new features, environment/configuration changes
Rules the exam tests: regression happens at all levels and in all SDLCs; with many changes, regression can target affected areas rather than everything; a passing confirmation test doesn't mean the fix caused no regressions elsewhere — both coexist.

Test suites in regression automation (2.2.4)

📖 Memorise — smoke suite When regression suites become huge: run the full/complete regression suite before major releases, and smaller selection-based suites for everyday changes — e.g., a smoke test suite: "does the build work at all?" — the most important functions, run on every new build.
⚠️ A smoke suite does not replace regression testing; it just gates further work on a build.

4 level × 4 type (যেকোনো type যেকোনো level-এ চলে), confirmation বনাম regression, আর smoke suite — Ch 2-এর নম্বরের প্রাণকেন্দ্র।

Level = scope · Type = nature — দুটি স্বাধীন অক্ষ; যেকোনো type যেকোনো level-এ চালানো যায়।

Test suites in regression automation (2.2.4)

📖 Memorise — smoke suite Regression suite যখন বিশাল হয়ে যায়: বড় release-এর আগে পুরো/complete regression suite চালান, আর দৈনন্দিন change-এর জন্য ছোট, selection-ভিত্তিক suite — যেমন smoke test suite: "build-টা আদৌ চলে কি না?" — সবচেয়ে গুরুত্বপূর্ণ function গুলো, প্রতিটি নতুন build-এ চালানো হয়।
⚠️ Smoke suite regression testing-এর বিকল্প নয়; এটা শুধু একটি build-এ পরের কাজ শুরু করা যাবে কি না সেই গেট তৈরি করে।

2.3 Maintenance testing (2.3.1)

K2

After release, three events can force more testing: you change it, you move it, or you retire it.

In plain words: live systems get changed, moved, or shut down — each event triggers testing, sized by what the change could touch.

📖 Memorise — the 3 maintenance triggers Scope is driven by impact analysis of what changed and what the change could affect:
  1. Modification — planned enhancements, corrective fixes, emergency hotfixes.
  2. Migration — moving to another platform/OS/DB/server, incl. data migration; often needs conversion testing of data + regression on the new environment.
  3. Retirement — shutting down; testing may include data archiving/migration and, when replacing a system, testing the new environment and old-data handling.
Maintenance releases may require regression tests at all levels; scope is influenced by the risk of the change — the change and its ripple effects decide how much regression runs.

3টি ট্রিগার — modification, migration, retirement — আর scope ঠিক হয় change ও তার ripple effect-এর impact analysis দিয়ে।

📖 Memorise — 3টি maintenance ট্রিগার কী বদলালো আর সেই change কী কী-কে ছুঁতে পারে তার impact analysis-ই scope নির্ধারণ করে:
  1. Modification — পরিকল্পিত enhancement, corrective fix, emergency hotfix।
  2. Migration — অন্য platform/OS/DB/server-এ সরানো, data migration সহ; প্রায়ই data-র conversion testing + নতুন environment-এ regression লাগে।
  3. Retirement — বন্ধ করে দেওয়া; testing-এ থাকতে পারে data-র archiving/migration, আর কোনো সিস্টেম replace করলে নতুন environment ও পুরনো data সামলানো পরীক্ষা।
Maintenance release-এ সব level-এ regression test লাগতে পারে; change-এর risk-ই scope প্রভাবিত করে — কতটা regression চলবে তা change আর তার ripple effect ঠিক করে।

Knowledge check — say it out loud, then reveal

Say each answer out loud before revealing — 8 quick checks.

In plain words: answer each question aloud first, then click to check yourself.

1. A test exercises the interface between the payment module and the shopping cart. Level, and why?
Component integration — it exercises the interface between two components.
2. Can functional, non-functional, black-box and white-box testing all be performed at component level?
Yes — every test type can be applied at every test level; component tests are often white-box but functional, non-functional and black-box component tests are all valid.
3. A defect is fixed; you re-run its failing test and it passes. What have you done, and what is still missing?
Confirmation testing done; regression testing of surrounding areas still missing.
4. The company moves the application from on-premise to a cloud provider. Which maintenance trigger, and what two kinds of testing are involved?
Migration; data conversion testing + regression testing (on the new environment).
5. What is a smoke suite and what is it not?
A small high-value suite that gates further work on a build; not a substitute for regression testing.
6. Give two DevOps benefits and one challenge for testing.
Benefits: fast feedback, quicker fixes, shorter time-to-market. Challenge: pipeline/automation maintenance, new skills.
7. Define shift-left with both of its components.
(a) test work products earlier; (b) involve testers early for testability and defect prevention.
8. UAT performed at the customer's own offices by their staff: which testing form is this?
User acceptance testing at the users' site (beta-style).

৮টি recall check — প্রতিটির উত্তর হাতে-মুখে বলুন, তারপর মিলিয়ে নিন।

প্রশ্ন ১. একটি test, payment module আর shopping cart-এর মধ্যকার interface পরীক্ষা করছে। কোন level, আর কেন?

উত্তর ১. Component integration — এটি দুটি component-এর মধ্যকার interface পরীক্ষা করছে।

প্রশ্ন ২. Functional, non-functional, black-box আর white-box testing — কি component level-এ করা যায়?

উত্তর ২. হ্যাঁ — যেকোনো test type যেকোনো test level-এ প্রয়োগ করা যায়; component test প্রায়ই white-box হয়, তবে functional, non-functional ও black-box component test-ও সম্পূর্ণ বৈধ।

প্রশ্ন ৩. একটি defect ঠিক হলো; আপনি তার fail করা test আবার চালালেন আর এবার পাস করল। আপনি কী করলেন, আর এখনো কী বাকি?

উত্তর ৩. Confirmation testing হলো; চারপাশের এলাকার regression testing এখনো বাকি।

প্রশ্ন ৪. কোম্পানি অ্যাপ্লিকেশনটি on-premise থেকে cloud provider-এ সরাচ্ছে। কোন maintenance ট্রিগার, আর কোন দুই ধরনের testing জড়িত?

উত্তর ৪. Migration; data conversion testing + regression testing (নতুন environment-এ)।

প্রশ্ন ৫. Smoke suite কী, আর কী নয়?

উত্তর ৫. ছোট, উচ্চমূল্যের একটি suite যা একটি build-এ পরের কাজ চালানো যাবে কি না সেই গেট দেয়; regression testing-এর বিকল্প নয়।

প্রশ্ন ৬. Testing-এর জন্য DevOps-এর দুটি benefit আর একটি challenge বলুন।

উত্তর ৬. Benefits: দ্রুত feedback, দ্রুত fix, ছোট time-to-market। Challenge: pipeline/automation রক্ষণাবেক্ষণ, নতুন skill।

প্রশ্ন ৭. Shift-left সংজ্ঞায়িত করুন তার দুই অংশসহ।

উত্তর ৭. (a) work product আগেভাগে test করা; (b) testability ও defect prevention-এর জন্য tester-দের শুরুতেই যুক্ত করা।

প্রশ্ন ৮. গ্রাহকের নিজের অফিসে তাদের কর্মীরা UAT চালাচ্ছে: এটি কোন রূপের testing?

উত্তর ৮. User-দের site-এ user acceptance testing (beta-ধাঁচের)।

1. In a sequential (V-model) project, detailed test design begins from documentation well before executable code exists. This illustrates that:

d — test design needs a basis, not executable code.

2. Which is a challenge testing faces in a DevOps environment?

b — pipeline/automation maintenance and new skills are the DevOps challenges; DevOps speeds feedback and automation enables regression, never replaces it.

3. "Shift-left" in testing means:

c — both halves: early work-product testing + early tester involvement.

4. After each sprint, the team discusses what went well and what to improve in testing. This is:

a — retrospective = post-iteration improvement meeting.

5. Testing that a single class correctly calculates VAT, isolated from the rest of the system using stubs, is:

a — isolated single component = component testing.

6. Testing the data exchanged between the invoicing module and the tax module is:

b — interfaces/interactions between components = component integration testing.

7. End-to-end testing of the complete, integrated system against its requirements and use cases is:

a — whole-system behaviour against requirements = system testing.

8. Users at their own workplace verify the system supports their business processes before rollout. This is:

c — users validating business fit at their own site (beta-style, UAT form); alpha is at the developer's site.

9. Operational acceptance testing is typically performed by:

b — operational acceptance = ops/admin staff.

10. Which statement about functional and non-functional testing is TRUE?

d — all four types at all levels — the key insight.

11. A tester derives tests from the system's specification without seeing the code. The derivation basis makes this:

a — spec-based derivation without internal knowledge = black-box.

12. A defect in the search function is fixed. The team re-runs the test that previously failed. This is:

d — re-running the failed test for that defect = confirmation.

13. After installing the search fix, the team also retests checkout and login "just in case." This is:

c — checking unaffected areas after a change = regression.

14. Regression testing:

b — regression follows any change, at any level.

15. A build is deployed to the test environment and a small suite verifies its most crucial functions work before deeper testing starts. This suite is:

b — smoke suite = build-worthiness gate.

16. The company upgrades the database from version 11 to 12 and re-checks data integrity and application behaviour. The maintenance trigger is:

d — new DB version = migration (incl. data conversion checks).

17. A 15-year-old system is replaced by a new one; old data must be archived and verified. The maintenance trigger is:

c — shutting down the old system = retirement (incl. archiving).

18. The scope of maintenance testing is primarily determined by:

b — impact analysis scopes maintenance testing.

19. In an iterative/agile project, which testing concern grows the most over time?

a — each iteration adds functionality → ever-growing regression need.

20. Emergency fixes deployed to production typically require:

b — even emergency fixes need confirmation + regression of affected areas.
