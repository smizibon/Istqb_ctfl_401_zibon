4.1 The test design process

K2

In plain words: turn "what to test" into concrete test cases through three ordered steps — analysis, design, implementation.

Test analysis → design → implementation chain, exact case/procedure/condition vocabulary, and risk-based prioritisation.

A test technique is a procedure to derive and select test cases — it makes testing reproducible, measurable, reviewable rather than ad-hoc. Black-box = from the specification/usage; white-box = from internal structure; experience-based = from skill/intuition.

Test analysisidentify test conditions from the test basis — what to test
→
Test designconditions → concrete test cases (inputs, expected results, coverage items) — how to test
→
Test implementationprocedures/suites, environments & data, confirm testability

During execution, actual results are compared with expected results; completion criteria (often coverage) show when to stop.

📖 Memorise — vocabulary, exactly • Test case = set of preconditions, inputs (incl. data), actions, expected results and postconditions; concrete (exact values) or logical/abstract.
• Test procedure = ordered sequence of test cases (script).
• Test condition = the "thing to test" identified from the test basis.
• Traceability: conditions ↔ basis ↔ cases ↔ results → enables coverage measurement, change-impact analysis, auditing, reporting.
🧠 Understand — prioritisation (4.1.2) Test cases are prioritised by risk (likelihood & impact of failure), coverage goals, and project constraints (time, budget). Highest priority runs first; in regression only high-priority subsets may run.

test analysis → design → implementation শৃঙ্খল, case/procedure/condition-এর নির্দিষ্ট শব্দার্থ, আর risk-ভিত্তিক prioritisation।

Test technique হলো test case বের করে আনা ও বাছাই করার একটা পদ্ধতি — এটা testing-কে খেয়ালখুশির বদলে পুনরাবৃত্তিযোগ্য, পরিমাপযোগ্য ও পর্যালোচনাযোগ্য করে তোলে। Black-box মানে specification বা ব্যবহার থেকে; white-box মানে অভ্যন্তরীণ গঠন থেকে; experience-based মানে দক্ষতা ও অন্তর্দৃষ্টি থেকে।

Test analysistest basis থেকে test condition চিহ্নিত করা — কী টেস্ট করব
→
Test designcondition থেকে সুনির্দিষ্ট test case (ইনপুট, expected result, coverage item) — কীভাবে টেস্ট করব
→
Test implementationprocedure/suite, পরিবেশ ও test data তৈরি, testability নিশ্চিত করা

Execution-এর সময় actual result-এর সঙ্গে expected result মিলিয়ে দেখা হয়; completion criteria (প্রায়ই coverage) বোঝায় কখন থামা যাবে।

📖 মুখস্থ করো — শব্দার্থ, হুবহু • Test case = precondition, ইনপুট (test data সহ), action, expected result ও postcondition-এর সেট; concrete (সুনির্দিষ্ট মান) বা logical/abstract হতে পারে।
• Test procedure = নির্দিষ্ট ক্রমে সাজানো test case-গুলোর সেট (স্ক্রিপ্ট)।
• Test condition = test basis থেকে চিহ্নিত "যেটা টেস্ট করতে হবে" সেই জিনিস।
• Traceability: condition ↔ basis ↔ case ↔ result → এর ফলে coverage মাপা, change-impact বিশ্লেষণ, audit ও রিপোর্টিং সবই সম্ভব হয়।
🧠 বুঝে নাও — prioritisation (4.1.2) Test case-গুলোর অগ্রাধিকার ঠিক হয় risk (failure-এর সম্ভাবনা ও প্রভাব), coverage লক্ষ্য, আর প্রকল্পের সীমাবদ্ধতার (সময়, বাজেট) ভিত্তিতে। সবচেয়ে বেশি priority-রটা আগে চালানো হয়; regression-এ শুধু high-priority ভাগটুকুই চলতে পারে।

4.2.1 Equivalence Partitioning (EP) — K3

K3

In plain words: group inputs the system treats the same way; test one value per group, invalids separately.

EP: count partitions, invalids get their own test — the minimum-test-count question lives here.

The rule

Divide inputs (or outputs, or internal values) into partitions whose members are handled identically — then one representative per partition is enough. Exhaustive testing is impossible (principle 2); EP is the systematic escape.

Traps

⚠️ Trap — invalid partitions Each invalid partition gets its OWN test case (one invalid value per test) so the right error can be verified. Never bundle several invalid values into one test — defect masking: several invalid values in one test case can mask each other, as the first rejection hides the others' behaviour. Forgetting invalid partitions entirely is trap #1.

Worked example

✏️ Worked example — hotel loyalty discount Rule: "Discount for guests aged 18–60; under-18 and over-60 get no discount but different messages."

Valid partitions: P1 = 18–60 (discount), P2 = under 18 (message A), P3 = over 60 (message B). Different behaviour → two separate valid partitions; if the spec treated them identically, they'd be one.
Invalid (age must be 0–120): P4 = below 0, P5 = above 120, P6 = non-numeric.
Minimum 6 tests: 25, 10, 70, −5, 200, "abc".
Exam pattern: "how many test cases minimum?" → count partitions (invalids individually). "Which value tests an invalid partition?" → the one outside valid ranges.

EP: partition গুনো, invalid গুলো পায় নিজের আলাদা test — সর্বনিম্ন test সংখ্যার প্রশ্ন এখানেই আসে।

ইনপুট (বা আউটপুট, বা অভ্যন্তরীণ মান) ভাগ করো এমন partition-এ (সমভাবা ভাগ), যেখানকার প্রতিটি সদস্যকে সিস্টেম একইভাবে সামলায় — তারপর প্রতিটি partition থেকে একজন প্রতিনিধি যথেষ্ট। সম্পূর্ণ নিরিক্ষণ অসম্ভব (principle 2); EP হলো সেখান থেকে বেরিয়ে আসার সুশৃঙ্খল পথ।

⚠️ Trap — invalid partition প্রতিটি invalid partition পায় তার নিজের আলাদা test case (এক test-এ একটির বেশি invalid মান নয়) — যাতে সঠিক error-টা যাচাই করা যায়। কখনোই একাধিক invalid মান এক test-এ জমা কোরো না — defect masking: এক test case-এ কয়েকটি invalid মান থাকলে প্রথম rejection-ই বাকিগুলোর আচরণ ঢেকে দেয়। Invalid partition একেবারে ভুলে যাওয়াই trap #1।
✏️ Worked example — হোটেল loyalty discount নিয়ম: "Discount for guests aged 18–60; under-18 and over-60 get no discount but different messages."

Valid partition: P1 = 18–60 (discount), P2 = 18-এর নিচে (message A), P3 = 60-এর উপরে (message B)। আচরণ আলাদা, তাই দুটি পৃথক valid partition; spec যদি দুটোকে একইভাবে দেখতো, তাহলে একটাই হতো।
Invalid (বয়স হতে হবে 0–120): P4 = 0-এর নিচে, P5 = 120-এর উপরে, P6 = সংখ্যা নয়।
ন্যূনতম ৬টি test: 25, 10, 70, −5, 200, "abc"।
পরীক্ষার প্যাটার্ন: "how many test cases minimum?" → partition গুনো (invalid আলাদা করে)। "Which value tests an invalid partition?" → valid range-এর বাইরের মানটি।

4.2.2 Boundary Value Analysis (BVA) — K3

K3

In plain words: bugs hide at the edges — test each boundary and the values just beside it.

BVA: test the boundary AND its neighbours — 2-value {b, neighbour}, 3-value {b−1, b, b+1}; the exam counts them.

Defects cluster at partition edges (off-by-one errors). BVA tests values on and around the boundary — and it can apply to inputs and outputs (also data ranges, screen positions, array sizes).

2-value method (ISTQB default)for each boundary b: {b, nearest neighbour} (from the adjacent partition). Range 18–60 → 18, 17, 60, 61
3-value methodfor each boundary b: {b−1, b, b+1}. Range 18–60 → 17, 18, 19 and 59, 60, 61
2-value = {b, neighbour} · 3-value = {b−1, b, b+1} — never mix conventions; "3-value" means each boundary contributes 3 tests.
✏️ Worked example — BVA on 18–60 2-value: 17, 18, 60, 61 (4 tests). 3-value: 17, 18, 19, 59, 60, 61 (6 tests). The neighbours are what make it BVA — giving only 18 and 60 is the classic wrong answer.

BVA: boundary এবং তার neighbour — দুটোই টেস্ট করো — 2-value {b, neighbour}, 3-value {b−1, b, b+1}; পরীক্ষায় এগুলোই গোনানো হয়।

Defect জমা হয় partition-এর কিনারায় (off-by-one error)। BVA boundary-র ওপরে-নামে ও চারপাশের মান টেস্ট করে — আর এটা ইনপুট ও আউটপুট দুই জায়গাতেই প্রযোজ্য হতে পারে (এছাড়া data range, স্ক্রিনের অবস্থান, array-র আকারেও)।

2-value method (ISTQB-র ডিফল্ট)প্রতিটি boundary b-এর জন্য: {b, নিকটতম neighbour} (পাশের partition থেকে)। Range 18–60 → 18, 17, 60, 61
3-value methodপ্রতিটি boundary b-এর জন্য: {b−1, b, b+1}। Range 18–60 → 17, 18, 19 এবং 59, 60, 61
2-value = {b, neighbour} · 3-value = {b−1, b, b+1} — নিয়ম দুটো কখনো মেশাবে না; "3-value" মানে প্রতিটি boundary থেকে ৩টি test।
✏️ Worked example — 18–60 রেঞ্জে BVA 2-value: 17, 18, 60, 61 (৪টি test)। 3-value: 17, 18, 19, 59, 60, 61 (৬টি test)। Neighbour-গুলোই একে BVA করে তোলে — শুধু 18 আর 60 দিলে সেটাই ক্লাসিক ভুল উত্তর।

4.2.3 Decision tables — K3

K3

In plain words: list every combination of conditions; each column (rule) needs at least one test.

Rules = product of condition values; each rule is a test — and collapsing identical-action rules cuts the exam's test count.

For business rules combining conditions, list every combination and the resulting action. One column per combination = a rule; each rule = at least one test. Full rules = product of condition values (2 binary conditions → 4; 3 binary → 8; e.g. 2×2×3 = 12).

✏️ Worked example — gold / €100 discount "Gold AND order > 100€ → 20%. Gold and ≤100€ → 5%. Non-gold and >100€ → 10%. Non-gold and ≤100€ → none."
Conditions \ RulesR1R2R3R4
Gold memberTTFF
Order > 100€TFTF
Action: discount20%5%10%none
→ 4 rules → 4 test cases minimum.
🧠 Understand — collapsing tables When a condition doesn't affect the action, merge rules with "don't care" (−): if gold members always got 20% regardless of amount, R1/R2 merge → Gold=T, Order=−, 20%. Collapsing reduces test count — the exam may ask how many tests after collapsing. But only collapse when the behaviour is identical — collapsing rules whose actions differ is a trap.

Rule = condition মানগুলোর গুণফল; প্রতিটি rule একটি test — আর একই action-এর rule মিশিয়ে (collapsing) পরীক্ষার test সংখ্যা কমে যায়।

একাধিক condition মিলিয়ে বিজনেস রুলের জন্য প্রতিটি সমাবেশ আর তার ফলে কী action হবে তা সাজিয়ে লেখো। প্রতিটি সমাবেশ = এক কলাম = একটি rule; প্রতিটি rule = অন্তত একটি test। পূর্ণ টেবিলের rule সংখ্যা = condition মানগুলোর গুণফল (২টি binary condition → 4; ৩টি binary → 8; যেমন 2×2×3 = 12)।

✏️ Worked example — gold / €100 discount "Gold AND order > 100€ → 20%. Gold and ≤100€ → 5%. Non-gold and >100€ → 10%. Non-gold and ≤100€ → none."
Conditions \ RulesR1R2R3R4
Gold memberTTFF
Order > 100€TFTF
Action: discount20%5%10%none
→ ৪টি rule → ন্যূনতম ৪টি test case।
🧠 বুঝে নাও — collapsed table কোনো condition যদি action-এ কোনো প্রভাব না ফেলে, তাহলে "don't care" (−) চিহ্ন দিয়ে rule মিশিয়ে দাও: gold member যদি পরিমাণ যা-ই হোক সবসময় 20% পেতো, তাহলে R1/R2 মিশে যেত → Gold=T, Order=−, 20%। Collapsing-এ test সংখ্যা কমে — পরীক্ষায় জিজ্ঞেস করতে পারে collapse করার পরে কতটি test। কিন্তু আচরণ হুবহু এক না হলে কখনোই collapse কোরো না — action আলাদা হয়ে গেলে rule মেশানো নিজেই একটা trap।

4.2.4 State transition testing — K3

K3

In plain words: draw circles (states) and arrows (transitions); count arrows for the exam, not circles.

Count TRANSITIONS, not states; test invalid (event, state) pairs too — 0-switch covers each single valid transition.

Behaviour depends on current state + event. Vocabulary (memorise): state = the condition the system is in; transition = change of state caused by an event, possibly with an action; action ≠ transition (action = output performed; may occur without changing state).

✏️ Worked example — ATM PIN state machine
Valid transitions (0-switch style): test each once — 4 tests: card inserted; wrong PIN; 3rd wrong PIN; card removed.

Invalid transitions = (event, state) pairs not in the diagram (e.g., card removed while Awaiting PIN) — each is also a test: the system should reject it, ideally without changing state. Frequently forgotten by candidates.
Count TRANSITIONS, not states. "Test all valid transitions" ≠ "test all states" — a state may have several in/out transitions.

N-switch coverage (concept only at FL): 0-switch covers every single valid transition; 1-switch covers every pair of consecutive transitions; higher N → more thorough, more tests.

গুনো TRANSITION, state নয়; invalid (event, state) জোড়াও টেস্ট করো — 0-switch প্রতিটি একক valid transition ঢেকে দেয়।

আচরণ নির্ভর করে বর্তমান state + event-এর ওপর। শব্দার্থ (মুখস্থ): state = সিস্টেম যে অবস্থায় আছে; transition = কোনো event-এর কারণে state বদল — সঙ্গে action থাকতেও পারে, নাও পারে; action ≠ transition (action = সম্পাদিত আউটপুট; state না বদলেও ঘটতে পারে)।

✏️ Worked example — ATM PIN state machine
Awaiting card—card inserted→Awaiting PIN—wrong PIN (<3)→Awaiting PIN—3rd wrong PIN→Card retained—card removed→Awaiting card
Valid transition (0-switch ধাঁচে): প্রতিটি একবার টেস্ট — ৪টি test: card inserted; wrong PIN; 3rd wrong PIN; card removed।

Invalid transition = ডায়াগ্রামে নেই এমন (event, state) জোড়া (যেমন Awaiting PIN অবস্থায় card removed) — প্রতিটিও একটি test: সিস্টেমকে সেটা reject করা উচিত, আদর্শভাবে state না বদলেই। পরীক্ষার্থীরা প্রায়ই এগুলো ভুলে যায়।
গুনো TRANSITION, state নয়। "Test all valid transitions" ≠ "test all states" — একটি state-এ কয়েকটি ভেতরে/বাইরে transition থাকতে পারে।

N-switch coverage (FL স্তরে শুধু ধারণা): 0-switch প্রতিটি একক valid transition ঢেকে দেয়; 1-switch পরপর দুটি transition-এর প্রতিটি জোড়া ঢেকে দেয়; N বড় হলে → আরও পূর্ণাঙ্গ, আরও বেশি test।

4.3 White-box: statement & branch coverage — K3

K3

In plain words: measure which lines and which decision outcomes your tests actually execute.

Compute % executed statements vs decision outcomes; 100% branch always implies 100% statement — never the reverse.

Based on the code's/design's internal structure.

  • Statement coverage = % of executable statements executed. 100% ⇒ every line runs at least once.
  • Branch coverage = % of decision outcomes exercised — each if has True and False exits; each case and default is a branch; loops: enter/skip. 100% ⇒ every outcome of every decision taken.
📖 Memorise — the exam-critical theorem
100% branch coverage
100% statement coverage
100% branch ⊃ 100% statement — always implies it. Never the reverse: a test set can run every statement while always taking the same branch outcome.
✏️ Worked example — the x>0 snippet (answers most coverage questions) 
1  if (x > 0):          # decision D
2      print("positive")
3  print("done")
Statements: 1, 2, 3 (three). Branches: D-T and D-F (two).
Test x=5: covers statements 1,2,3 → 100% statement, 50% branch (D-F never taken).
Adding x=−1 → 100% branch.
Coverage measure (exam style): "tests execute 8 of 10 statements" → 80% statement coverage. To raise branch coverage, add a test that exercises the untaken decision outcome.
⚠️ Trap — coverage proves nothing about correctness White-box coverage measures structural test thoroughness but cannot detect missing functionality — code never written produces 0% extra statements to cover. Guaranteed trap: "100% branch coverage means the system meets all requirements" → false.

execute হওয়া statement বনাম decision outcome-এর % বের করো; 100% branch সবসময় 100% statement-এর অন্তর্ভুক্ত — কখনোই উল্টোটা নয়।

ভিত্তি কোড বা design-এর অভ্যন্তরীণ গঠন।

  • Statement coverage = executable statement-এর কত % execute হলো। 100% ⇒ প্রতিটি লাইন অন্তত একবার চলল।
  • Branch coverage = কত % decision outcome অনুশীলিত হলো — প্রতিটি if-এর True ও False দুটি পথ; প্রতিটি case ও default একেকটি branch; loop: ঢোকা/বাদ দেওয়া। 100% ⇒ প্রতিটি decision-এর প্রতিটি outcome নেওয়া হলো।
📖 মুখস্থ করো — পরীক্ষা-নির্ণায়ক উপপাদ্য
100% branch coverage
100% statement coverage
100% branch ⊃ 100% statement — সবসময় এটাই অন্যটাকে বোঝায়। কখনোই উল্টোটা নয়: একটি test set প্রতিটি statement চালিয়েও সবসময় একই branch outcome নিতে পারে।
✏️ Worked example — x>0 স্নিপেট (coverage প্রশ্নের বেশিরভাগ উত্তর এখানেই) 
1  if (x > 0):          # decision D
2      print("positive")
3  print("done")
Statement: 1, 2, 3 (তিনটি)। Branch: D-T ও D-F (দুটি)।
Test x=5: statement 1,2,3 ঢেকে যায় → 100% statement, 50% branch (D-F কখনো নেওয়া হয়নি)।
x=−1 যোগ করলে → 100% branch।
Coverage মাপা (পরীক্ষার স্টাইল): "tests execute 8 of 10 statements" → 80% statement coverage। Branch coverage বাড়াতে হলে এমন test যোগ করো যেটা এখনো নেওয়া হয়নি এমন decision outcome অনুশীলন করে।
⚠️ Trap — coverage সঠিকতার কোনো প্রমাণ দেয় না White-box coverage structural সূক্ষ্মতা মাপে, কিন্তু অনুপস্থিত functionality ধরতে পারে না — যে কোড লেখাই হয়নি, সেখানে ঢাকার মতো নতুন কোনো statement নেই-ই। নিশ্চিত trap: "100% branch coverage means the system meets all requirements" → মিথ্যা।

4.5 Collaboration-based approaches (K2 — new in v4.0)

K2

In plain words: derive tests from acceptance criteria; "Given/When/Then" in the question means BDD.

Acceptance-criteria testing, ATDD (test-first), BDD (Given/When/Then as living documentation) — spot the keyword, pick the label.

  • Acceptance criteria-based testing (4.5.1): derive tests from user-story acceptance criteria (the story's validation conditions); good criteria make stories testable — Given/When/Then style conditions help.
  • ATDD: tests derived from acceptance criteria before coding — the test-first loop with developers, testers, and business together.
  • BDD: collaboration where examples with business value are written in a domain-specific, structured language (Given/When/Then — Gherkin), usable as living documentation and automation. Scenario says "Given/When/Then" → BDD.
🧠 Understand — choosing a technique Black-box for functional coverage of requirements; add white-box to measure/raise structural coverage; add experience-based where time or specs are limited or risk intuition matters. In practice techniques are combined.

Acceptance criteria থেকে টেস্ট, ATDD (test-first), BDD (Given/When/Then যেন living documentation) — কীওয়ার্ড চিনলেই লেবেল বসে যায়।

  • Acceptance criteria-based testing (4.5.1): user story-র acceptance criteria থেকে test তৈরি (story পাস করার শর্তগুলো); ভালো criteria story-কে টেস্টযোগ্য করে তোলে — Given/When/Then ধাঁচের শর্ত সেটা সহজ করে।
  • ATDD: কোডিংয়ের আগেই acceptance criteria থেকে test লেখা — developer, tester ও business মিলেমিলে test-first লুপ।
  • BDD: এমন সহযোগিতা যেখানে বিজনেস মূল্যসহ example লেখা হয় ডোমেইন-নির্দিষ্ট কাঠামোবদ্ধ ভাষায় (Given/When/Then — Gherkin), যা living documentation ও automation হিসেবে ব্যবহারযোগ্য। Scenario-তে "Given/When/Then" দেখলেই → BDD।
🧠 বুঝে নাও — technique বাছাই Requirement-এর functional coverage-র জন্য black-box; structural coverage মাপতে/বাড়াতে white-box যোগ করো; সময় বা spec কম হলে বা risk-অনুমান জরুরি হলে experience-based যোগ করো। বাস্তবে technique-গুলো মিলিয়ে ব্যবহার হয়।

C3. A numeric field 0–120 drives three behaviours (0–12, 13–64, 65–120); non-numeric input is also possible. Minimum EP test cases, invalids counted individually?

d — 3 valid partitions + 3 invalid (<0, >120, non-numeric), each invalid separately → 6. Bundling invalids (b) risks defect masking.

C4. Code: if order > 100: freeShipping(). So far only order=150 has been tested. Which additional test raises branch coverage?

b — only the False outcome of the decision is untaken; 80 (≤ 100) exercises it. a/c re-take True; d) repeats the same outcome.

C5. A form has two independent fields: field X with 3 partitions, field Y with 2 partitions. Fields are tested independently (no combination table required). Minimum EP test cases?

a — number of EP test cases = SUM of partitions across fields when tested independently: 3 + 2 = 5. The product (3 × 2 = 6) applies only if a full combination table is required.

C6. A loan system rates income as "low" (≤ 20,000), "medium" (> 20,000 and ≤ 60,000) or "high" (> 60,000). Using output-based EP, how many tests cover every equivalence class of output?

c — equivalence classes of OUTPUTS: one representative input per class (e.g., 10k, 40k, 70k) → 3 tests. b) confuses output classes with input invalid partitions; d) is exhaustive testing.
