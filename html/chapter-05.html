5.1 Test planning & estimation

K2

Write down why/what/when/who/how; start and stop only on countable criteria; estimate from past data or expert judgement; pyramid & quadrants classify your tests.

In plain words: think of it like a pilot's pre-takeoff checklist — nobody flies (or stops) on a feeling.

5.1.1 Planning

Planning defines why, what, when, who, how — aligned with stakeholders and organisational goals. The plan may be standalone or part of a sprint plan; planning is continuous and adapts as context changes. Typical content: strategy, scope, entry/exit criteria, estimates, risks, environment definition.

📖 Memorise — Entry & exit criteria (5.1.2) Entry criteria — what must hold to begin execution (environment ready, test data available, testable build). Starting too early wastes effort on false failures.
Exit criteria — what must hold to declare testing complete (planned tests executed, coverage achieved, defects below threshold, no critical opens). Agile cousin: Definition of Done.
⚠️ Criteria must be measurable — “the system feels stable” is the exam’s favourite anti-pattern.
Entry gate ✅
environment ready · test data available · testable build
“system feels stable” ✗
→
Test execution
→
Exit gate 🏁
≥95% planned tests run · coverage achieved · 0 open critical defects
“feels stable enough” ✗

5.1.3 Estimation

🧠 Understand — Estimation (5.1.3) Metrics-based = estimate from measures of past projects (tests/hour, defects/test, velocity). Giveaway phrase: “historical data”.
Expert-based = estimate from experience of experts (planning poker, wideband Delphi). Giveaway: “the senior tester estimates…”. Practise combining both.

5.1.4 Prioritisation

Prioritisation (5.1.4): order execution by risk, coverage goals, constraints — so if time runs out, the most valuable tests have already run.

5.1.5 The test pyramid

FEW · large end-to-end / system tests — slow, costly
FEWER · integration tests
MANY · small automated component (unit) tests — fast, cheap
You want most tests at the base. Too many GUI tests → long feedback loops.

5.1.6 The test quadrants

Q1 · technology-facing, supports the teamcomponent & integration tests, often automated
Q2 · business-facing, supports the teamfunctional examples, ATDD/BDD-style tests
Q3 · business-facing, critiques the productacceptance, exploratory, usability, UAT
Q4 · technology-facing, critiques the productnon-functional: performance, security, reliability
← technology-facing · business-facing →  |  ↑ supports team · critiques product ↓
⚠️ TrapPerformance testing is Q4, technology-facing — examiners love parking it in a business-facing quadrant.

Plan মানে কেন/কী/কখন/কে/কীভাবে; মাপা যায় এমন entry/exit criteria; metrics- বনাম expert-based estimation; test pyramid ও test quadrants।

Planning (5.1.1) ঠিক করে দেয় কেন, কী, কখন, কে, কীভাবে — stakeholder আর সংস্থার লক্ষ্যের সঙ্গে মিলিয়ে। Plan আলাদা দলিল হতে পারে, আবার sprint plan-এর অংশও হতে পারে; planning একটি continuous প্রক্রিয়া — পরিস্থিতি বদলালে plan-ও মানিয়ে নেয়। সাধারণ বিষয়াবলি: strategy, scope, entry/exit criteria, estimate, risk, environment definition।

📖 মুখস্থ করো — Entry ও exit criteria (5.1.2) Entry criteria — execution শুরু করতে হলে কী কী পূরণ থাকতে হবে (environment প্রস্তুত, test data available, testable build)। খুব আগে শুরু করলে false failure-এ শ্রম নষ্ট হয়।
Exit criteria — testing সম্পূর্ণ ঘোষণা করতে হলে কী কী পূরণ থাকতে হবে (planned test চালানো হয়েছে, coverage অর্জিত, defects সীমার নিচে, কোনো critical open নেই)। Agile-এর আত্মীয়: Definition of Done।
⚠️ Criteria অবশ্যই measurable হতে হবে — “the system feels stable” জাতীয় কথাই পরীক্ষার প্রিয় anti-pattern।
🧠 বোঝো — Estimation (5.1.3) Metrics-based = অতীত প্রকল্পের measure থেকে estimate (tests/hour, defects/test, velocity)। চেনার শব্দ: “historical data”।
Expert-based = expert-দের অভিজ্ঞতা থেকে estimate (planning poker, wideband Delphi)। চেনার শব্দ: “the senior tester estimates…”। দুটো একসঙ্গে মেলানোর অভ্যাস করো।

Prioritisation (5.1.4): risk, coverage-এর লক্ষ্য আর constraint অনুযায়ী execution-এর ক্রম সাজাও — যাতে সময় শেষ হয়ে আসার আগেই সবচেয়ে মূল্যবান test গুলো চলে যায়।

5.1.5 The test pyramid

FEW · large end-to-end / system tests — ধীর, ব্যয়বহুল
FEWER · integration tests
MANY · ছোট automated component (unit) test — দ্রুত, সস্তা
টেস্টের অধিকাংশ থাকা উচিত ভিত্তিতে (base-এ)। GUI test বেশি হলে feedback loop দীর্ঘ হয়ে যায়।

5.1.6 The test quadrants

Q1 · technology-facing, supports the teamcomponent ও integration test, প্রায়ই automated
Q2 · business-facing, supports the teamfunctional উদাহরণ, ATDD/BDD-ধাঁচের test
Q3 · business-facing, critiques the productacceptance, exploratory, usability, UAT
Q4 · technology-facing, critiques the productnon-functional: performance, security, reliability
← technology-facing · business-facing →  |  ↑ supports team · critiques product ↓
⚠️ TrapPerformance testing is Q4, technology-facing — পরীক্ষকরা একে business-facing quadrant-এ রাখতে বড় ভালোবাসেন; ওখানে রাখা যাবে না।

5.2 Risk & risk-based testing

K2

Score each risk by multiplying likelihood × impact, handle the biggest number first, and report what risk remains.

In plain words: think of it like triage in an emergency room — treat the highest score first, not the scariest-looking.

📖 Memorise Risk = likelihood × impact. Risk analysis determines the level; risk assessment = identify + analyse + define mitigation. Testing itself is a mitigation activity. Risk-based testing attacks the riskiest items first, most intensely — and the risk that remains afterwards is residual risk, which must be communicated to stakeholders.
Exam skill: rank by multiplication, never eyeball — A = 2×5 = 10, B = 4×3 = 12, so B is the higher risk and gets tested first, with the strongest technique.

Read it like this: A sits at likelihood 2 × impact 5 = 10; B at 4 × 3 = 12. B scores higher despite A's scarier impact — multiply, never eyeball.

📖 Memorise — Product vs project risk (5.2.3) Product risk — the work product may fail its users: security holes, poor usability, bad data, unreliable behaviour. (“Customer data might leak.”)
Project risk — threats to the project itself: staffing, skills, conflicts, supplier trouble, bad estimates, scope creep, tool issues. (“The tool vendor may go bankrupt.” “The release might be late.”)

Risk = likelihood × impact — গুণ করে rank করো; product বনাম project ভাগ আলাদা; residual risk জানাতে হয়।

📖 মুখস্থ করো Risk = likelihood × impact। Risk analysis নির্ধারণ করে risk-এর মাত্রা; risk assessment = চিহ্নিত করা + analysis করা + mitigation ঠিক করা। Testing নিজেই একটি mitigation কাজ। Risk-based testing সবচেয়ে ঝুঁকিপূর্ণ item-গুলোকে আগে ও সবচেয়ে জোরালোভাবে আক্রমণ করে — তারপরেও যে risk থেকে যায়, সেটাই residual risk, যা stakeholder-দের কাছে জানাতেই হবে।
Exam skill: কখনো চোখ বুজে অনুমান নয়, গুণ করে rank করো — A = 2×5 = 10, B = 4×3 = 12, তাই B-ই বেশি ঝুঁকিপূর্ণ; ওটাই আগে test হবে, আর সবচেয়ে শক্তিশালী কৌশলে।
📖 মুখস্থ করো — Product বনাম project risk (5.2.3) Product risk — work product ব্যবহারকারীদের কাছে ব্যর্থ হতে পারে: security-র ফাঁক, খারাপ usability, ভুল data, অবিশ্বস্ত আচরণ। (“Customer data might leak.”)
Project risk — প্রকল্পটির নিজের ওপর হুমকি: staffing, skills, দ্বন্দ্ব, supplier ঝামেলা, ভুল estimate, scope creep, tool-এর সমস্যা। (“The tool vendor may go bankrupt.” “The release might be late.”)

5.3 Monitoring, control & completion

K2

Watch progress against the plan, act when it drifts, report to fit the reader, and close out with a report and archived testware.

In plain words: think of it like a car dashboard — monitoring is glancing at the gauges, control is turning the wheel.

Monitoring & control

  • Monitoring = gather data, compare progress vs plan. Control = act on it — re-prioritise, adjust schedule, add automation. (Observe → correct.)

Reporting & metrics

  • Reports fit the audience: management gets a short summary of cost, schedule, quality, risk; the test team gets execution detail.
  • Metrics to know: planned-vs-executed tests, pass rate, defect find/fix trends, defect density, requirements/code coverage, residual risk. They answer: on track? good enough? when to stop?

Test completion

  • Test completion happens at milestones (release, end of iteration, end of a test level): check exit criteria, write the completion report (results vs plan, obstacles, lessons learned, residual risk), archive testware.

5.4 Configuration management

Testware (plans, cases, data, automation) must be version-controlled, traceable, change-managed — so the right testware matches the right build, results are reproducible, nothing is lost. Scenario giveaway: “tests ran against the wrong build” or “nobody could find the latest test cases” → CM failure.

Monitoring মানে plan-এর সঙ্গে তুলনা করে দেখা, control মানে ব্যবস্থা নেওয়া; report পাঠক অনুযায়ী সাজানো; completion মানে exit criteria, report, archive; CM testware-এর version নিয়ন্ত্রণ করে।

  • Monitoring = data জোগাড় করে progress আর plan-এর তুলনা করা। Control = সেই তথ্যের ভিত্তিতে ব্যবস্থা নেওয়া — re-prioritise, schedule ঠিক করা, automation যোগ করা। (দেখা → সংশোধন।)
  • Report পাঠক অনুযায়ী: management পায় cost, schedule, quality, risk-এর ছোট সারাংশ; test team পায় execution-এর বিস্তারিত।
  • যে metrics জানতে হবে: planned বনাম executed test, pass rate, defect find/fix trend, defect density, requirements/code coverage, residual risk। এগুলোর উত্তর দেয়: গতি ঠিক আছে কি না, মান যথেষ্ট কি না, কখন থামব।
  • Test completion ঘটে milestone-এ (release, iteration-এর শেষ, কোনো test level-এর শেষ): exit criteria যাচাই করা, completion report লেখা (ফলাফল বনাম plan, বাধা, lessons learned, residual risk), testware archive করা।

5.4 Configuration management

Testware (plan, case, data, automation) অবশ্যই version-controlled, traceable, change-managed হতে হবে — যাতে সঠিক testware মেলে সঠিক build-এর সঙ্গে, ফলাফল reproducible হয়, কিছুই হারিয়ে না যায়। Scenario-র চেনা লক্ষণ: “tests ran against the wrong build” বা “nobody could find the latest test cases” → CM-এর ব্যর্থতা।

5.5 Defect management — the K3 home

K3

A defect walks a loop — New → Assigned → Fixed → confirmed → Closed — and a good report gives anyone the steps, expected vs actual, build and severity to reproduce it. No blame.

In plain words: think of it like a hospital referral slip — where it is, who has it, and exactly how to see the symptom again.

Lifecycle (memorise the loop)

⚠️ Trap“Fixed” is not the end: the confirmation test precedes closing. A failing confirmation reopens the defect.

A good defect report contains (5.5.2 — K3)

  • Unique ID · concise, searchable title · date & reporter
  • Environment / build under test
  • Steps to reproduce — ordered, precise
  • Expected vs actual result (both!)
  • Severity (technical impact); priority if the org uses it
  • Evidence (logs, screenshots), references (test case, requirement), status
📖 Memorise — Severity vs priority Severity = technical impact (“crashes when saving”). Priority = business urgency (“must fix before the demo”). They diverge: homepage typo on launch eve = low severity, high priority.
🧠 K3 question pattern“Which report is best / what should be added?” → reward: reproducible steps, expected and actual, build ID. Penalise: blame (“Sam’s fault”), vagueness (“crashes sometimes”), several defects bundled in one report, missing expected result.

Lifecycle New→Assigned→Fixed→Confirmation→Closed; ভালো report = steps, expected বনাম actual, build, severity — দোষারোপ নয়।

Lifecycle (flow-টা মুখস্থ করো)

New→Assigned→Fixed→Confirmation test→ pass করলে →Closed
fail করলে → Reopened ↺ আবার Assigned-এ ফেরে পাশের state: Rejected · Duplicate · Deferred
⚠️ Trap“Fixed” is not the end — অর্থাৎ “Fixed” মানেই শেষ নয়: defect বন্ধ করার আগে confirmation test অবশ্যই চলে। Confirmation fail করলে defect আবার Reopened হয়ে যায়।

একটি ভালো defect report-এ যা থাকে (5.5.2 — K3)

  • Unique ID · ছোট, খোঁজা যায় এমন title · তারিখ ও reporter
  • Environment / build under test
  • Steps to reproduce — ক্রমানুসারে, নির্দিষ্ট করে লেখা
  • Expected বনাম actual result (দুটোই!)
  • Severity (technical impact); সংস্থা ব্যবহার করলে priority
  • Evidence (log, screenshot), reference (test case, requirement), status
📖 মুখস্থ করো — Severity বনাম priority Severity = technical impact (“crashes when saving”)। Priority = ব্যবসায়িক তাড়া (“must fix before the demo”)। দুটো এক হয় না, আলাদা দিকে যেতে পারে: launch-এর আগের রাতে homepage-এর ছোট্ট typo = কম severity, বেশি priority।
🧠 K3 প্রশ্নের ধাঁচ“Which report is best / what should be added?” → পুরস্কার পায়: reproduce করা যায় এমন steps, expected এবং actual, build ID। শাস্তি পায়: দোষারোপ (“Sam’s fault”), অস্পষ্ট ভাষা (“crashes sometimes”), এক report-এ কয়েকটি defect গাদাগাদি, expected result না থাকা।

Knowledge check — say it out loud, then reveal

10 recall checks — say each answer aloud, then reveal.

In plain words: if you can say it out loud without peeking, it's exam-ready.

1. Two measurable exit criteria for system test?
e.g. ≥95% planned cases executed; zero open critical defects; agreed coverage achieved.
2. Planning poker sizes testing work — which technique?
Expert-based estimation (team judgement, not historical measures).
3. Rank: A = 2×5, B = 4×3 — which is tested first?
A = 10, B = 12 → B first. Multiply, never eyeball.
4. “Test tool vendor may go bankrupt” — product or project risk?
Project risk (threatens delivery, not product quality).
5. Four quadrants with one example each?
Q1 component tests · Q2 BDD/functional examples · Q3 exploratory/UAT · Q4 performance/security.
6. What does 100% branch coverage as exit criterion NOT guarantee?
Absence of defects — and it can’t detect missing functionality.
7. “Payment broken again, Sam’s fault. Please fix.” — three report defects?
Blame; no steps; no expected/actual result; no build/environment; vague — any three.
8. State after “Fixed”, and what decides the next one?
Confirmation test; pass → Closed, fail → Reopened.
9. Why more component than end-to-end tests in the pyramid?
Higher levels are slower, costlier, harder to maintain — long feedback loops.
10. Two metrics for management, two for the team?
Mgmt: cost/schedule summary, defect trends, residual risk. Team: planned-vs-executed, pass rate, coverage detail.

প্রশ্ন ১. System test-এর জন্য দুটো measurable exit criteria? — উত্তর: যেমন ≥95% planned case চালানো হয়েছে; কোনো open critical defect নেই; সম্মত coverage অর্জিত।

প্রশ্ন ২. Planning poker দিয়ে testing-এর কাজের আকার মাপা হয় — এটা কোন কৌশল? — উত্তর: Expert-based estimation (দলের বিচারবুদ্ধি, অতীতের measure নয়)।

প্রশ্ন ৩. Rank: A = 2×5, B = 4×3 — কোনটা আগে test হবে? — উত্তর: A = 10, B = 12 → আগে B। গুণ করো, চোখে দেখে অনুমানে নয়।

প্রশ্ন ৪. “Test tool vendor may go bankrupt” — product না project risk? — উত্তর: Project risk (deliverable-এর গুণমানে নয়, delivery-র ওপর হুমকি)।

প্রশ্ন ৫. চারটি quadrant, প্রতিটির একটি করে উদাহরণ? — উত্তর: Q1 component test · Q2 BDD/functional উদাহরণ · Q3 exploratory/UAT · Q4 performance/security।

প্রশ্ন ৬. Exit criteria হিসেবে 100% branch coverage কী নিশ্চয়তা দেয় না? — উত্তর: defect নেই — এমন নিশ্চয়তা দেয় না; আর অনুপস্থিত functionality ধরতেও পারে না।

প্রশ্ন ৭. “Payment broken again, Sam’s fault. Please fix.” — report-টির তিনটি ত্রুটি? — উত্তর: দোষারোপ; steps নেই; expected/actual result নেই; build/environment নেই; অস্পষ্ট — যেকোনো তিনটি।

প্রশ্ন ৮. “Fixed”-এর পরের state কোনটি, আর পরেরটা কী ঠিক করে? — উত্তর: Confirmation test; pass করলে Closed, fail করলে Reopened।

প্রশ্ন ৯. Pyramid-এ end-to-end-এর বদলে component test বেশি কেন? — উত্তর: উপরের স্তর ধীর, ব্যয়বহুল, রক্ষণাবেক্ষণ কঠিন — feedback loop দীর্ঘ হয়ে যায়।

প্রশ্ন ১০. Management-এর জন্য দুটি, দলের জন্য দুটি metric? — উত্তর: Management: cost/schedule সারাংশ, defect trend, residual risk। দল: planned বনাম executed, pass rate, coverage-এর খুঁটিনাটি।

⏱ 60-second recap

Plan = why · what · when · who · how Entry = ready to start · Exit = done enough — both measurable Risk = likelihood × impact Product risk = QUALITY of product vs Project risk = DELIVERY Severity = TECHNICAL impact vs Priority = BUSINESS urgency Defect lifecycle = New→Assigned→Fixed→Confirmed→Closed, fail ↺ Reopened Good report = reproducible: steps, expected vs actual, build Estimation = metrics-based (past data) vs expert-based (judgement)

Exercises — closed book, click to answer (target 16/20)

Interactive quiz, target 16/20 — instant feedback.

1. Which of the following is a MEASURABLE exit criterion?

b — countable thresholds make criteria measurable; feelings don’t.

2. Entry criteria primarily prevent:

b — that is their stated purpose (prevent wasted effort & false failures).

3. Estimating from defect counts and velocity of previous releases is:

b — “measures of past projects” is the giveaway for metrics-based.

4. Planning poker to size testing tasks is:

b — judgement of the participants, no historical data needed.

5. The test pyramid recommends:

c — broad automated base, narrow slow top.

6. Performance and security testing belong to which quadrant?

d — non-functional tests critique the product from a technology angle.

7. Risk level is calculated as:

b — the formula, memorise it cold.

8. A: likelihood 3, impact 2. B: likelihood 1, impact 9. Which justifies more effort?

b — 9 > 6; the highest risk gets the strongest testing.

9. “Customer credit card data could be exposed by a weak payment module.” This is a:

a — the product might fail its users (quality problem).

10. “The test tool vendor may withdraw support mid-project.” This is a:

d — threatens the project’s success, not the deliverable’s quality.

11. Risk-based testing reduces:

a — residual risk is never zero and must be reported.

12. Comparing progress against the plan, then re-prioritising when behind, are respectively:

a — observe & compare = monitoring; act & correct = control.

13. A report for senior management should be:

c — audience-tailored reporting; managers want dashboards, not detail.

14. Which metric helps decide whether testing can stop?

a — trends + exit criteria answer “when can we stop?” A design count says nothing about execution or defect status.

15. Test completion activities include all EXCEPT:

d — busywork that pads execution counts, not a completion activity; the other three are canonical completion activities.

16. Configuration management of testware ensures:

b — versioning, traceability, reproducibility.

17. In the defect lifecycle, the state after “Fixed” is typically:

d — confirmation precedes closure. Trap answer “a” skips the re-test.

18. Which set of elements makes a defect report USABLE?

c — the K3 field list; anyone can reproduce and evaluate.

19. A minor cosmetic typo on the homepage one day before a major public launch is likely:

d — tiny technical impact, big business urgency: severity and priority diverge.

20. Residual risk means:

a — what’s left after your mitigations; communicate it, never hide it.
