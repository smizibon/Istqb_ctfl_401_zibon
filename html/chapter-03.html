3.1 Static testing basics

K2

Read, don't run. People (reviews) and tools (static analysis) check documents and code before anything executes — catching defects early, cheaply, and sometimes that dynamic testing can never see.

In plain words: reading the work product carefully instead of running it.

Definition: static testing examines work products without executing the code — manually (reviews) or automatically (static analysis). It works on any work product: requirements, user stories, epics, code, design models, test plans, tests, contracts — anything that can be read.

🧠 Understand — the key exam point Static testing finds defects directly in work products, early (shift-left) and cheaply. It can detect defects that dynamic testing would only find as failures at much higher cost — or not at all.

Typical findings per work-product type

📖 Memorise — findings lists Requirements: ambiguities, contradictions, omissions, duplicates, impractical designs, security holes in design, testability problems (a requirement that can't be verified)

Code: syntax errors (some), incorrectly spelled variables, undeclared variables, unreachable/duplicate code, excessive complexity, security vulnerabilities, coding-standard violations

Representations (models): missing steps, incorrect steps, wrong order

Reviews vs. static analysis (3.1.2)

ReviewsStatic analysis
HowHuman examination of documents/codeTool-based analysis of code (and models)
FindsDeviations from standards/requirements, defects, improvement points, misunderstandingsStructure-related defects: unreachable code, undeclared/mis-spelled variables, duplicate code, excessive complexity, security vulnerabilities, standards violations
NeedsPeople, preparation, meeting or async examinationTool, runs continuously (often inside IDE/CI)

3.1.3 Strengths of static analysis: finds defects before dynamic testing can, can find defects hard or impossible to observe at runtime (e.g., unreached code), prevents defect injection improving maintainability. Tool examples: compilers (yes — a compiler is a static analysis tool), static code analysers (linters, SonarQube-style), security analysers, checkers for coding standards. A tool described as flagging "unused variable" or "cyclomatic complexity too high" without running the program → static analysis.

⚠️ Trap Static testing finds the defect in the document/code itself; dynamic testing observes failures from which defects are inferred. Static testing does not need runnable code or test execution.

কোড execute না করেও কাজ হয়: review (মানুষ) আর static analysis (tool) দিয়ে document বা code-এর defect খুব আগেই, কম খরচে ধরা যায় — এমন defect-ও ধরা পড়ে যেগুলো dynamic testing কখনোই দেখতে পাবে না।

সংজ্ঞা: static testing (স্ট্যাটিক টেস্টিং) হলো work product পরীক্ষা করা কোড execute না করে — হাতে (review) অথবা স্বয়ংক্রিয়ভাবে (static analysis)। এটা যেকোনো work product-এ চলে: requirements, user story, epic, code, design model, test plan, test, contract — যা পড়া যায় তা-ই।

🧠 বুঝে নাও — পরীক্ষার মূল পয়েন্ট static testing সরাসরি work product-এর ভেতরের defect ধরে, খুব আগে (shift-left) এবং কম খরচে। এমন defect-ও এটা ধরতে পারে যেগুলো dynamic testing হয় অনেক বেশি খরচে failure হিসেবে ধরতে পেত, নয়তো একেবারেই পারত না।

প্রতি ধরনের work product-এ সাধারণত যা পাওয়া যায়

📖 মুখস্থ করো — findings-এর তালিকা Requirements: অস্পষ্টতা, পরস্পরবিরোধ, বাদ পড়ে যাওয়া বিষয়, duplicate, অবাস্তব design, design-এ নিরাপত্তা ফাঁক, testability সমস্যা (এমন requirement যার যাচাই করা যায় না)

Code: syntax error (কিছু কিছু), ভুল বানানের variable, undeclared variable, unreachable/duplicate code, অতিরিক্ত complexity, security vulnerability, coding standard লঙ্ঘন

Representation (model): ধাপ বাদ পড়া, ভুল ধাপ, ভুল ক্রম

Review বনাম static analysis (3.1.2)

ReviewsStatic analysis
কীভাবেdocument/code পরীক্ষা করে মানুষcode (এবং model) বিশ্লেষণ করে tool
কী খুঁজে বের করেstandard/requirements থেকে বিচ্যুতি, defect, উন্নতির পয়েন্ট, ভুল বোঝাবুঝিগঠন-সংক্রান্ত defect: unreachable code, undeclared/ভুল বানানের variable, duplicate code, অতিরিক্ত complexity, security vulnerability, standard লঙ্ঘন
কী লাগেমানুষ, প্রস্তুতি, মিটিং বা async পরীক্ষাTool, চলতে থাকে (প্রায়ই IDE/CI-র ভেতরে)

3.1.3 Static analysis-এর শক্তি: dynamic testing-এর আগেই defect ধরে, এমন defect-ও পায় যা runtime-এ দেখা কঠিন বা অসম্ভব (যেমন unreachable code), defect ঢোকানো আটকে দিয়ে maintainability বাড়ায়। Tool-এর উদাহরণ: compiler (হ্যাঁ — compiler নিজেই একটা static analysis tool), static code analyser (linter, SonarQube-ধাঁচের), security analyser, coding standard যাচাইয়ের tool। কোনো tool প্রোগ্রাম না চালিয়েই "unused variable" বা "cyclomatic complexity too high" বলে ফ্ল্যাগ করলে → সেটা static analysis।

⚠️ ফাঁদ Static testing ধরে document/code-এর ভেতরের defect; dynamic testing দেখে failure, সেখান থেকে defect অনুমান করা হয়। static testing-এর জন্য runnable code বা test execution লাগে না।

3.2 The review process

K2

From casual pair-checking to full-formal inspections, four review types climb a formality ladder — and six named roles split the work. Learn which type is which, and who does what.

In plain words: how reviews run, and who plays which part.

Benefits of early reviews / feedback loop (3.2.1)

BenefitWhat it means
Early feedbackDefects caught cheaply, before code exists
Shorter feedback loopProblems surface sooner, so rework shrinks
Defect preventionBetter inputs (e.g., requirements) mean fewer defects injected into later products
Knowledge spreadAuthor learns standards; reviewers learn the product
Consistency & maintainabilityWork products become more consistent, maintainable and testable

Review types (3.2.3) — the formality ladder

Informal→ Walkthrough→ Technical review→ Inspection

Formality rises with: moderator-not-author · defined roles · entry/exit criteria · metrics & checklists

TypeFormalityKey characteristics
Informal reviewLowestNo process, no roles, no documents; pair review / pair programming, desk-check; cheap, immediate feedback; main objective: cheap and fast defect detection
WalkthroughMid-lowLed by the author; goal often education / consensus-building, gathering comments, explaining/evaluating; scenarios and dry runs possible
Technical reviewMid-highTrained moderator (not the author), technical/qualified reviewers; peer review among technical peers; objectives: consensus, detect defects, make decisions, generate alternatives
InspectionHighestMost formal: rules/checklists, defined roles, detailed entry/exit criteria, metrics gathered, formal follow-up; led by a trained moderator (not the author); objectives: maximum defect detection, quality improvement, process improvement

Exam logic: "author presents to the team to reach shared understanding" = walkthrough; "rule-based, checklist, metrics, trained moderator" = inspection.

In plain words: walkthrough — the author walks the team through it; inspection — the full-formal, checklist-and-metrics review; informal — the cheapest, chat-over-the-desk check; technical review — qualified peers with a trained moderator.

Review roles (3.2.2)

K1

📖 Memorise — the six roles
AuthorCreated the work product; fixes defects after the review
Facilitator (moderation)Ensures the review runs effectively: planning, running the meeting, neutral conduct
Reviewer (inspector)Reviews the product; ideally not the author, may be subject-matter experts
Scribe (recorder)Collects defects/comments during the meeting
Review leaderTakes overall responsibility for the review: planning, decides exit, follow-up
ManagerDecides whether a review happens and its objectives; accounts for review outcomes; not necessarily present in the meeting
A person may hold multiple roles; small reviews merge them. Exam scenarios: "who records the issues raised?" → scribe; "who ensures an effective meeting?" → facilitator; "who decides on executing the review?" → manager.

Review success factors (3.2.4)

  • Right reviewers (mix of expertise)
  • Adequate preparation time (typically ≥ meeting time)
  • Review rate limits (pages/hour caps — small chunks beat marathons)
  • Defect-focused, no-blame culture (critique the product, never the person; "egoless")

Confusion table

Easily confusedDistinction
Static / dynamic testingWithout execution / with execution

Walkthrough / technical reviewAUTHOR-led, educational / PEER-based, defect- and decision-focused, trained moderator
Technical review / inspectionPeer consensus & decisions / MOST FORMAL: rules, checklists, metrics, entry/exit criteria

⚠️ Traps • "Reviews are only about finding defects" → they also spread knowledge, build consensus, improve consistency and maintainability.
• "Reviews require a meeting" → informal and many reviews can be asynchronous, no meeting needed.

ফরমালিটির মই (informal → walkthrough → technical review → inspection), সঙ্গে ছয়টা review role — যেগুলো মুখস্থ করতেই হবে।

আগেভাগে review-এর উপকারিতা / feedback loop (3.2.1)

Review আগে মতামত দেয় (code-এর আগেই, কম খরচে defect ধরা যায়), feedback loop ছোট করে, আর defect prevention-এ সাহায্য করে: work product (যেমন requirements) review করে উন্নত করলে পরের ধাপের product-এ ঢুকে যাওয়া defect কমে। এছাড়া review জ্ঞান ছড়ায় (author standard শেখে; reviewer product শেখে), consistency বাড়ায়, আর এমন work product তৈরি করে যা আরও maintainable ও testable।

Review-এর ধরন (3.2.3) — ফরমালিটির মই

Informal→ Walkthrough→ Technical review→ Inspection

Formality বাড়ে এসবের সঙ্গে: moderator author নন · নির্দিষ্ট role · entry/exit criteria · metrics ও checklist

TypeFormalityKey characteristics
Informal reviewসবচেয়ে কমকোনো process নেই, role নেই, document নেই; pair review / pair programming, desk-check; সস্তা, সাথে সাথে মতামত; মূল লক্ষ্য: সস্তা ও দ্রুত defect ধরা
Walkthroughকম-মাঝারিপরিচালনা করেন author; লক্ষ্য প্রায়ই শেখানো / ঐকমত্য তৈরি, মন্তব্য সংগ্রহ, ব্যাখ্যা/মূল্যায়ন; দৃশ্যকাহিনী (scenario) ও dry run হতে পারে
Technical reviewমাঝারি-বেশিপ্রশিক্ষিত moderator (author নন), technical/যোগ্য reviewer; technical সমপর্যায়ের peer-দের মধ্যে peer review; লক্ষ্য: ঐকমত্য, defect ধরা, সিদ্ধান্ত নেওয়া, বিকল্প তৈরি করা
Inspectionসর্বোচ্চসবচেয়ে formal: নিয়ম/checklist, নির্দিষ্ট role, বিস্তারিত entry/exit criteria, metrics সংগ্রহ, formal follow-up; পরিচালনা করেন প্রশিক্ষিত moderator (author নন); লক্ষ্য: সর্বোচ্চ defect ধরা, গুণগত উন্নতি, process-এর উন্নতি

পরীক্ষার যুক্তি: "author দলের কাছে বুঝিয়ে বলে, সবার সমঝোতা তৈরি হয়" = walkthrough; "নিয়মভিত্তিক, checklist, metrics, প্রশিক্ষিত moderator" = inspection।

Review-এর role (3.2.2)

📖 মুখস্থ করো — ছয়টি role

Facilitator (moderation)review কার্যকরভাবে চলা নিশ্চিত করেন: পরিকল্পনা, মিটিং পরিচালনা, নিরপেক্ষ আচরণ
Reviewer (inspector)product পরীক্ষা করেন; আদর্শভাবে author নন, subject-matter expert হতে পারেন
Scribe (recorder)মিটিং চলাকালে defect/মন্তব্য সংগ্রহ করেন
Review leaderreview-এর সামগ্রিক দায়িত্ব নেন: পরিকল্পনা, exit ঠিক করা, follow-up
Managerঠিক করেন review হবে কি না এবং এর লক্ষ্য কী; review-এর ফলাফলের জবাবদিহি করেন; মিটিংয়ে উপস্থিত থাকার দরকার নেই

Review সফল হওয়ার শর্ত (3.2.4)

  • সঠিক reviewer (expertise-র সঠিক মিশ্রণ)
  • পর্যাপ্ত প্রস্তুতির সময় (সাধারণত মিটিংয়ের সময়ের সমান বা বেশি) এবং review-এর হারের সীমা (প্রতি ঘণ্টায় পৃষ্ঠার সীমা — লম্বা ম্যারাথনের চেয়ে ছোট ছোট ভাগ ভালো)
  • Defect-কেন্দ্রিক, দোষারোপহীন সংস্কৃতি (product-এর সমালোচনা করো, মানুষের নয়; "egoless")
  • Management-এর review-কে মূল্যবান মনে করে সমর্থন দেওয়া (সময় বরাদ্দ)
  • স্পষ্ট উদ্দেশ্য এবং উদ্দেশ্য অনুযায়ী সঠিক review-এর ধরন

Knowledge check — say it, then reveal

Eight quick recall drills. Say each answer out loud before opening it; miss two or more and go back over 3.1–3.2.

In plain words: cover the answer, speak it, then check.

1. A linter flags an unreachable branch without the program running. Static or dynamic, review or analysis?
Static testing via static analysis.
2. Who leads a walkthrough, and who must never lead an inspection?
Walkthrough: the author leads. Inspection: a trained moderator who is NOT the author.
3. Which review type produces metrics and uses checklists with formal entry/exit criteria?
Inspection.
4. Name three defects a review can find in requirements.
Ambiguities, contradictions, omissions, duplicates, impractical designs, security issues, testability problems (any three).
5. Why can static analysis find defects that dynamic testing cannot?
It examines structure; some defects (e.g., unreachable code) are never exercised at runtime.
6. Which role decides whether a review is performed?
The manager.
7. Is a compiler a static analysis tool? Justify.
Yes — it analyses code without executing it.
8. Give three review success factors.
Right reviewers with expertise; adequate preparation time with capped review rates; blame-free, defect-focused culture (any three).

প্রশ্ন ৮. Review সফল হওয়ার তিনটি শর্ত বলো।

উত্তর: সঠিক reviewer যাদের expertise আছে; পর্যাপ্ত প্রস্তুতির সময় ও সীমিত review-এর হার; দোষারোপমুক্ত, defect-কেন্দ্রিক সংস্কৃতি (যেকোনো তিনটি)।

⏱ 60-second recap

Static = no execution — read it, don't run it Reviews = human · static analysis = tool 4 types on the formality ladder: informal (cheapest) → walkthrough (author-led) → technical review (peers, trained moderator) → inspection (most formal: checklists + metrics) 6 roles, one job each: scribe records, facilitator runs the meeting, leader is responsible, manager decides A compiler IS a static analysis tool Success = right people + enough time (rate caps) + no blame

Exercises — closed book (target 12/15)

Fifteen multiple-choice questions, closed book. Aim to get twelve or more right before Friday.

In plain words: no notes, no peeking — just you vs the questions.

1. Static testing differs from dynamic testing because static testing:

b — the definition of static testing.

2. Which finding is typical for static testing of a requirements document?

b — document defects: ambiguity, contradiction, omission; a, c, d are runtime (dynamic) observations.

3. A tool reports an unused variable and an unreachable branch without running the program. This is:

c — tool-based, no execution = static analysis.

4. Which of these is a static analysis tool?

d — a compiler analyses code without running it — a legitimate static analysis tool.

5. Static analysis can find defects that dynamic testing cannot because it:

b — structure-level defects (unreachable code, unused variables) may never surface at runtime.

6. In a review, the person who collects comments and defects raised during the meeting is the:

c — scribe records; facilitator runs the meeting.

7. The review role responsible for the review's overall success, including planning and follow-up, is the:

a — the review leader owns the review end-to-end.

8. Who decides whether a review is performed at all, and its objectives?

b — the manager decides execution of reviews and their objectives.

9. A review led by the author to explain the design to the team and gather comments is a:

a — author-led, educational/consensus = walkthrough.

10. The most formal review type, with rules, checklists, metrics, entry/exit criteria and a trained moderator who is not the author, is:

d — all formality markers = inspection.

11. Pair reviewing a colleague's test cases at their desk, no documents, no formal roles — this is:

d — no process/roles/documents = informal review.

12. Which is a typical objective of a technical review?

b — technical review objectives: consensus, defects, decisions, alternatives.

13. Which statement about reviews is TRUE?

c — reviews also educate and harmonise; they complement, never replace, dynamic testing.

14. A review descends into personal blame and the author becomes defensive. Which success factor was violated?

d — blame-free culture is a documented success factor.

15. To keep reviews effective, work products should be reviewed:

b — capped review rates in small chunks keep reviewer effectiveness.
