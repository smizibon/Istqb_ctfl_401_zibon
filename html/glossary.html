Chapter 1 — Fundamentals (13 terms)

The vocabulary everything else is built on: the quality chain, QA/QC, the principles, and the basis/condition/case family.

Software testingK2

"the process of evaluating a work product to determine whether it satisfies requirements" and to detect differences between given and expected results.

Software testing মানে একটি work product মূল্যায়ন করা, যাতে বোঝা যায় এটি requirements পূরণ করে কি না — execution ছাড়াও planning, analysis, design, implementation, reporting সবই এর অংশ।

Ch 1 §1.1 →

Testing vs debuggingK2

"Testing detects failures caused by defects. Debugging finds, analyses, and removes their causes."

Testing failure শনাক্ত করে; debugging কারণ খুঁজে, analysis করে, দূর করে। Debugging একটি development activity।
⚠️ An option describing "finding and removing causes" is debugging, not testing.

Ch 1 §1.1 →

Error (mistake)K2

"a human action that produces a defect."

Error মানে মানুষের কাজ (human action) যা defect তৈরি করে — developer spec ভুল পড়ে ভুল formula টাইপ করল।
⚠️ An error is always a human action — "environmental conditions" as an error cause = wrong; as a failure cause = correct.

Ch 1 §1.2 →

Defect (bug/fault)K2

"a flaw in a work product, can cause failure."

Defect মানে work product-এর ভেতরে একটি ত্রুটি, যা failure ঘটাতে পারে — code-এ ভুল interest formula আছে।
⚠️ A defect does not always cause a failure — the wrong code may never be executed, or the inputs may never trigger it.

Ch 1 §1.2 →

FailureK2

"actual behaviour deviates from expected, observed at runtime."

Failure মানে প্রকৃত আচরণ প্রত্যাশিত আচরণ থেকে সরে যায়, runtime-এ দেখা যায় — ATM ভুল balance দেখাল।
⚠️ Not every failure comes from a code defect — environmental conditions (radiation, hardware faults, wrong setup/configuration) can cause failures.

Ch 1 §1.2 →

Test oracleK2

"if the expected result was wrong (bad oracle), a 'failure' may be observed even when the system behaves as designed."

Oracle মানে expected result-এর উৎস — ভুল oracle (ভুল প্রত্যাশিত ফলাফল) থাকলে সিস্টে ঠিক থাকলেও "failure" দেখা দেয়।

Ch 1 §1.2 →

QA vs QCK2

"quality assurance (QA), process-oriented" — preventing defects through reviews and early test design; "quality control (QC), product-oriented" — detecting and evaluating defects.

QA process-মুখী প্রতিরোধ ("আমরা সঠিক কাজগুলো সঠিকভাবে করছি?"); QC product-মুখী শনাক্তকরণ ("এই build ভালো?")।
⚠️ Testing alone does not ensure quality — testing gives information about quality.

Ch 1 §1.2 →

Defect clusteringK2

"Few modules hold most defects" — 80% of bugs in 3 of 40 modules → focus effort there.

অল্প কিছু module-এই বেশিরভাগ defect থাকে — শক্তি সেখানেই কেন্দ্রীভূত করো।
⚠️ "Most bugs in a few modules" = defect clustering, NOT pesticide paradox.

Ch 1 §1.3 →

Pesticide paradoxK2

"Same tests stop finding new defects → update/improve the tests."

একই test নতুন defect খুঁজে পাওয়া বন্ধ করে দেয় → test update/improve করো।
⚠️ The remedy is new/modified tests, never "run them more often".

Ch 1 §1.3 →

Testing shows presence of defectsK2

"Testing can show the presence of defects, never their absence."

Testing defect-এর উপস্থিতি দেখাতে পারে, অনুপস্থিতি কখনোই নয় — সব test pass মানে bug-free নয়।
⚠️ "All tests passed, so the software is defect-free" → violates principle 1.

Ch 1 §1.3 →

Test basisK2

"the body of information a test is based on (requirements, user stories, design)."

Test basis মানে যে তথ্যভাণ্ডারের উপর ভিত্তি করে test করা হয় (requirements, user story, design)।

Ch 1 §1.4 →

Test conditionK2

"an item/event to be tested" ("interest calculation on overdue accounts").

Test condition মানে যে item/event test করা হবে — test analysis-এর কাজ condition চিহ্নিত করা (কী test করব)।

Ch 1 §1.4 →

Test caseK2

"input + execution preconditions + expected result" — the expected result is what makes it a case, not just a trial run.

Test case মানে input + precondition + expected result — expected result-ই একে প্রকৃত case বানায়; এটি test design-এর কাজ (কীভাবে test করব)।

Ch 1 §1.4 →

Chapter 2 — Testing in the SDLC (12 terms)

Shift-left, the 4 levels × 4 types, confirmation vs regression, smoke, and the maintenance triggers.

Shift-leftK2

"(a) testing work products earlier (reviews, static analysis, early test design) and (b) testers involved from the start in requirements/user stories."

Shift-left-এর দুই অর্ধেক: (a) work product আগেভাগে test, (b) শুরু থেকেই tester-দের যুক্ত করা — দুটো মিলেই সঠিক অর্থ।
⚠️ Shift-left described only as "starting test execution earlier" is incomplete.

Ch 2 §2.1 →

RetrospectiveK2

"the team reflects: what went well, what to improve — including test process improvement."

Iteration/release-এর পরে দলের প্রতিফলন-মিটিং — কী ভালো হলো, কী উন্নত করা যায়; exam scenario: "team meets after sprint to improve testing" → retrospective।

Ch 2 §2.1 →

Component (unit) testingK2

"Single components in isolation" — developers; "mock objects/stubs to isolate."

একটি component আলাদা করে টেস্ট — developers করেন, আলাদা করতে mock object/stub ব্যবহার হয়।

Ch 2 §2.2 →

Component integration testingK2

"Interactions & interfaces between components" — developers primarily.

component-গুলোর মধ্যে interaction ও interface পরীক্ষা — মূলত developers করেন।
⚠️ "Verifying interaction between modules" = component integration testing.

Ch 2 §2.2 →

System testingK2

"Whole system's behaviour & capabilities, end-to-end" — independent test team.

পুরো সিস্টেমের আচরণ ও সামর্থ্য, end-to-end — independent test team চালায়; functional + non-functional দুটোই।

Ch 2 §2.2 →

Acceptance testingK2

"Validation — meets user needs/business goals?; often the entry criterion for release."

Validation — user/business-এর চাহিদা মেটায় কি না; প্রায়ই release-এর entry criterion; users/customers, ops, support চালান।

Ch 2 §2.2 →

Alpha vs beta testingK2

"alpha (developer's site), beta (user's site)."

Alpha = developer-এর site-এ, beta = user-দের site-এ — দুটো acceptance testing-এর রূপ।
⚠️ Beta testing placed "at the developer's site" → swapped with alpha.

Ch 2 §2.2 →

Functional vs non-functional testingK2

Functional: "What the system does — functions it performs." Non-functional: "How well it behaves — quality characteristics."

Functional মানে সিস্টেম কী করে; non-functional মানে কতটা ভালোভাবে করে (performance, usability, security, reliability)।
⚠️ "Non-functional testing happens only at system level" → false; all types at all levels.

Ch 2 §2.2 →

Black-box vs white-box testingK2

Black-box: "Behaviour from outside, based on specifications — no knowledge of internals." White-box: "Internal structure of the system/code drives the tests."

Black-box মানে spec থেকে বাইরে থেকে আচরণ দেখা; white-box মানে ভেতরের গঠন থেকে test তৈরি।
⚠️ The real distinction is spec-based vs structure-based derivation — not "who runs it".

Ch 2 §2.2 →

Confirmation vs regression testingK2

Confirmation (re-testing): "Verify a specific defect is really fixed." Regression: "Verify a change broke nothing else."

Confirmation মানে নির্দিষ্ট defect সত্যিই ঠিক হয়েছে কি না; regression মানে change অন্য কিছু ভেঙেছে কি না — দুটো একসাথে থাকে।
⚠️ Regression runs after any change (fixes, new features, environment/config changes), at all levels, all SDLCs — not only after defect fixes.

Ch 2 §2.2 →

Smoke test suiteK2

"does the build work at all?" — the most important functions, run on every new build.

Smoke suite জিজ্ঞেস করে "build-টা আদৌ চলে কি না" — সবচেয়ে গুরুত্বপূর্ণ function গুলো, প্রতিটি নতুন build-এ।
⚠️ A smoke suite does not replace regression testing; it just gates further work on a build.

Ch 2 §2.2 →

Maintenance triggersK2

"Modification — planned enhancements, corrective fixes, emergency hotfixes. Migration — moving to another platform/OS/DB/server. Retirement — shutting down."

৩টি ট্রিগার: modification (enhancement/fix/hotfix), migration (নতুন platform/DB), retirement (বন্ধ করা) — scope ঠিক হয় impact analysis দিয়ে।
⚠️ A migration scenario needs data conversion testing too — not just regression testing.

Ch 2 §2.3 →

Chapter 3 — Static Testing (8 terms)

Static testing vs static analysis, the review formality ladder, and the six roles.

Static testingK2

"examines work products without executing the code — manually (reviews) or automatically (static analysis)."

Static testing মানে work product পরীক্ষা করা কোড execute না করে — হাতে (review) বা স্বয়ংক্রিয়ভাবে (static analysis)।
⚠️ Static testing finds the defect in the document/code itself; dynamic testing observes failures from which defects are inferred.

Ch 3 §3.1 →

Reviews vs static analysisK2

Reviews: "Human examination of documents/code." Static analysis: "Tool-based analysis of code (and models)."

Review করে মানুষ; static analysis করে tool — দুটোই execution ছাড়া চলে।
⚠️ A compiler is a static analysis tool — it analyses code without executing it.

Ch 3 §3.1 →

Informal reviewK2

"No process, no roles, no documents; pair review / pair programming, desk-check; cheap, immediate feedback."

কোনো process নেই, role নেই, document নেই — pair review, desk-check; মূল লক্ষ্য সস্তা ও দ্রুত defect ধরা।

Ch 3 §3.2 →

WalkthroughK2

"Led by the author; goal often education / consensus-building, gathering comments, explaining/evaluating."

Walkthrough পরিচালনা করেন author নিজে; লক্ষ্য প্রায়ই শেখানো / ঐকমত্য তৈরি ও মন্তব্য সংগ্রহ।

Ch 3 §3.2 →

Technical reviewK2

"Trained moderator (not the author), technical/qualified reviewers; peer review among technical peers."

প্রশিক্ষিত moderator (author নন) ও যোগ্য reviewer-দের peer review; লক্ষ্য: ঐকমত্য, defect ধরা, সিদ্ধান্ত, বিকল্প তৈরি।

Ch 3 §3.2 →

InspectionK2

"Most formal: rules/checklists, defined roles, detailed entry/exit criteria, metrics gathered, formal follow-up; led by a trained moderator (not the author)."

সবচেয়ে formal review: নিয়ম/checklist, নির্দিষ্ট role, entry/exit criteria, metrics, formal follow-up — পরিচালনা করেন প্রশিক্ষিত moderator (author নন)।
⚠️ "Rule-based, checklist, metrics, trained moderator" = inspection; "author presents to the team" = walkthrough.

Ch 3 §3.2 →

The six review rolesK1

Author (fixes defects after) · Facilitator (ensures effective running) · Reviewer (examines the product) · Scribe (collects defects/comments) · Review leader (overall responsibility) · Manager (decides whether a review happens).

ছয়টি role: author (পরে ঠিক করেন) · facilitator (মিটিং কার্যকর রাখেন) · reviewer (পরীক্ষা করেন) · scribe (issue লিখে রাখেন) · review leader (সামগ্রিক দায়িত্ব) · manager (review হবে কি না ঠিক করেন)।
⚠️ "Who records the issues raised?" → scribe; "who ensures an effective meeting?" → facilitator; "who decides on executing the review?" → manager.

Ch 3 §3.2 →

Facilitator / review leader / managerK1

"Runs the meeting / owns the review's success / decides the review happens."

Facilitator = মিটিং চালান; review leader = review-এর সাফল্যের মালিক; manager = review হবে কি না সেটা ঠিক করেন।

Ch 3 §3.2 →

Chapter 4 — Test Techniques (15 terms + 6 formulas)

The K3 recipe vocabulary: EP, BVA, decision tables, state transitions, statement/branch coverage — plus experience-based and collaboration-based labels. K3 technique cards link to the cheat sheet's K3 box.

Test procedure (test script)K2

"ordered sequence of test cases (script)" — the step-by-step instructions for executing test cases, in order.

Test procedure মানে নির্দিষ্ট ক্রমে সাজানো test case-গুলোর সেট (script) — test implementation-এর কাজ এটি তৈরি করা।

Ch 4 §4.1 →

TraceabilityK2

"conditions ↔ basis ↔ cases ↔ results → enables coverage measurement, change-impact analysis, auditing, reporting."

Traceability মানে test basis ↔ condition ↔ case ↔ result-এর সংযোগ — এতে coverage মাপা, impact analysis, audit ও reporting সম্ভব।

Ch 4 §4.1 →

Equivalence partitioning (EP)K3

"Divide inputs (or outputs, or internal values) into partitions whose members are handled identically — then one representative per partition is enough."

ইনপুট ভাগ করো এমন partition-এ, যেখানকার প্রতিটি সদস্যকে সিস্টেম একইভাবে সামলায় — তারপর প্রতিটি partition থেকে একজন প্রতিনিধি যথেষ্ট।
⚠️ Each invalid partition gets its OWN test case — forgetting invalid partitions entirely is trap #1. K3 recipe: cheat sheet · THE K3 BOX

Ch 4 §4.2.1 →

Defect maskingK3

"several invalid values in one test case can mask each other, as the first rejection hides the others' behaviour."

এক test case-এ কয়েকটি invalid মান থাকলে প্রথম rejection-ই বাকিগুলোর আচরণ ঢেকে দেয় — তাই এক test-এ একটির বেশি invalid মান নয়।
⚠️ Never bundle several invalid values into one test.

Ch 4 §4.2.1 →

Boundary value analysis (BVA)K3

"Defects cluster at partition edges (off-by-one errors). BVA tests values on and around the boundary — and it can apply to inputs and outputs."

Defect জমা হয় partition-এর কিনারায় — BVA boundary-র ওপরে-নিচে ও চারপাশের মান test করে; ইনপুট ও আউটপুট দুই জায়গাতেই প্রযোজ্য।
⚠️ 2-value (ISTQB default) = {b, nearest neighbour} → 18–60 gives 18, 17, 60, 61 · 3-value = {b−1, b, b+1} → 17, 18, 19, 59, 60, 61. Giving only 18 and 60 is the classic wrong answer. K3 recipe: cheat sheet · THE K3 BOX

Ch 4 §4.2.2 →

Decision tableK3

"One column per combination = a rule; each rule = at least one test. Full rules = product of condition values (2 binary conditions → 4; e.g. 2×2×3 = 12)."

প্রতিটি condition-সমাবেশ = এক কলাম = একটি rule; প্রতিটি rule = অন্তত একটি test; পূর্ণ টেবিলের rule = condition মানগুলোর গুণফল।

Ch 4 §4.2.3 → · cheat sheet · THE K3 BOX

Collapsing a decision tableK3

"When a condition doesn't affect the action, merge rules with 'don't care' (−)" — collapsing reduces test count.

কোনো condition-এর action-এ প্রভাব না থাকলে "don't care" (−) দিয়ে rule মিশিয়ে দাও — collapsing-এ test সংখ্যা কমে।
⚠️ Only collapse when the behaviour is identical — collapsing rules whose actions differ is a trap.

Ch 4 §4.2.3 →

State transition testingK3

"Behaviour depends on current state + event." 0-switch coverage "covers every single valid transition."

আচরণ নির্ভর করে বর্তমান state + event-এর ওপর; 0-switch প্রতিটি একক valid transition ঢেকে দেয়।
⚠️ Count TRANSITIONS, not states — "test all valid transitions" ≠ "test all states". K3 recipe: cheat sheet · THE K3 BOX

Ch 4 §4.2.4 →

Transition vs actionK3

"transition = change of state caused by an event, possibly with an action; action ≠ transition (action = output performed; may occur without changing state)."

Transition মানে event-এর কারণে state বদল; action মানে সম্পাদিত আউটপুট — action state না বদলেও ঘটতে পারে (ভুল PIN-এ error beep)।

Ch 4 §4.2.4 →

Invalid transitionsK3

"(event, state) pairs not in the diagram — each is also a test: the system should reject it, ideally without changing state."

ডায়াগ্রামে নেই এমন (event, state) জোড়া — প্রতিটিও একটি test; সিস্টেমকে সেটা reject করা উচিত। পরীক্ষার্থীরা প্রায়ই ভুলে যায়।

Ch 4 §4.2.4 →

Statement vs branch coverageK3

"Statement coverage = % of executable statements executed. Branch coverage = % of decision outcomes exercised."

Statement coverage = executable statement-এর কত % execute হলো; branch coverage = কত % decision outcome নেওয়া হলো — প্রতিটি if-এর True ও False দুটি পথ।
⚠️ 100% branch ⊃ 100% statement — always implies it, never the reverse. And coverage cannot detect missing functionality: "100% branch coverage means the system meets all requirements" → false. K3 recipe: cheat sheet · THE K3 BOX

Ch 4 §4.3 →

Error guessingK2

"Anticipate likely defects from experience and target them (division by zero, empty lists, nulls, special characters, date boundaries) — a defect-based technique."

অভিজ্ঞতা থেকে সম্ভাব্য defect আঁচ করে সরাসরি সেগুলোকে লক্ষ্য করা — একটি defect-ভিত্তিক technique।
⚠️ Error guessing is not a checklist technique — no list, pure anticipation.

Ch 4 §4.4 →

Checklist-based testingK2

"Test against a checklist from experience/standards; items may become conditions; checklist quality decides effectiveness."

অভিজ্ঞতা/মানদণ্ড থেকে তৈরি checklist-এর বিপরীতে test — checklist-এর মানেই effectiveness নির্ধারিত হয়; item আপডেট হতে থাকা উচিত।

Ch 4 §4.4 →

Exploratory testingK2

"Concurrent learning, test design, execution; charter-based (goal) and session-based (timeboxed, with reports)."

শেখা, test design ও execution একসাথে চলে; charter-ভিত্তিক (লক্ষ্য) ও session-ভিত্তিক (নির্দিষ্ট সময়ে, রিপোর্টসহ)।
⚠️ "Exploratory = random/unstructured" → false (charters, sessions, discipline).

Ch 4 §4.4 →

ATDD vs BDDK2

ATDD: "tests derived from acceptance criteria before coding." BDD: "examples with business value are written in a domain-specific, structured language (Given/When/Then — Gherkin), usable as living documentation."

ATDD মানে কোডিংয়ের আগেই acceptance criteria থেকে test; BDD-তে business-মূল্যসহ example লেখা হয় Given/When/Then (Gherkin)-এ — living documentation হিসেবে।
⚠️ Scenario says "Given/When/Then" → BDD.

ƒ EP — minimum test countK3

min tests = (# valid partitions) + (# invalid partitions) — one test per valid partition, and each invalid partition gets its own separate test (bundling invalids = defect masking). Valid 1–100 → 1 valid + invalids 0, 101, "abc" → 4 tests.

প্রতিটি valid partition-এ একটি test, আর প্রতিটি invalid partition-এ আলাদা test — একসাথে করলে defect masking হয়।

ƒ BVA 2-value — tests per boundaryK3

tests = 2 × (# boundaries) — test b and its nearest neighbour. Range 18–60: 2 boundaries → 18, 17, 60, 61 → 4 tests.

প্রতিটি boundary-তে দুটি value — b এবং তার পাশের neighbour। 18–60 মানে 18, 17, 60, 61।
⚠️ Giving only 18, 60 without neighbours is not BVA.

ƒ BVA 3-value — tests per boundaryK3

tests = 3 × (# boundaries) — test b−1, b, b+1. Range 18–60: 17, 18, 19, 59, 60, 61 → 6 tests.

প্রতিটি boundary-তে তিনটি value — b−1, b, b+1। 18–60 মানে 17, 18, 19 এবং 59, 60, 61।

Ch 4 §4.2 → · recipe ↗

ƒ Decision table — full rule countK3

full rules = product of each condition's values (2 binary conditions → 4; 3 binary → 8; 2×2×3 → 12). Minimum tests = collapsed rules — collapse ONLY when actions are identical.

Full rule সংখ্যা = প্রতিটি condition-এর value সংখ্যার গুণফল; শুধু identical action হলে collapse — min test = collapsed rule সংখ্যা।

Ch 4 §4.2 → · recipe ↗

ƒ State transition — test countK3

count transitions, not states; 0-switch coverage = every valid transition exercised once; each invalid (event, state) pair adds 1 more test → total = valid transitions + invalid pairs.

Test গণনা হয় transition দিয়ে, state দিয়ে নয়; প্রতিটি invalid (event, state) pair-ও একটি test।

Ch 4 §4.2 → · recipe ↗

ƒ Statement & branch coverage %K3

statement % = executed statements ÷ total statements × 100; branch % = outcomes exercised ÷ total outcomes × 100 (each two-way decision has 2 outcomes: e.g. 12 decisions → 24). Example: 36/40 statements = 90%; 20/24 outcomes = 83.3%.

Statement % = চালানো statement ÷ মোট statement × 100; branch % = চালানো decision outcome ÷ মোট outcome × 100 (দুই-মুখী decision-এ ২টি outcome)।
⚠️ 100% branch ⇒ 100% statement — never the reverse.

Chapter 5 — Test Management (12 terms + 1 formula)

Entry/exit criteria, estimation, pyramid & quadrants, risk, severity/priority, and the defect lifecycle.

Entry criteriaK2

"what must hold to begin execution (environment ready, test data available, testable build)."

Execution শুরু করতে হলে যা পূরণ থাকতে হবে — environment প্রস্তুত, test data available, testable build; খুব আগে শুরু করলে false failure-এ শ্রম নষ্ট।

Ch 5 §5.1 →

Exit criteriaK2

"what must hold to declare testing complete (planned tests executed, coverage achieved, defects below threshold, no critical opens)."

Testing সম্পূর্ণ ঘোষণা করতে হলে যা পূরণ থাকতে হবে; Agile-এর আত্মীয়: Definition of Done।
⚠️ Criteria must be measurable — "the system feels stable" is the exam's favourite anti-pattern.

Ch 5 §5.1 →

Metrics-based vs expert-based estimationK2

"Metrics-based = estimate from measures of past projects… Expert-based = estimate from experience of experts (planning poker, wideband Delphi)."

Metrics-based = অতীত প্রকল্পের measure থেকে ("historical data"); expert-based = expert-দের অভিজ্ঞতা থেকে (planning poker, wideband Delphi)।

Ch 5 §5.1 →

Test pyramidK2

"MANY · small automated component (unit) tests — fast, cheap" at the base; "FEW · large end-to-end / system tests — slow, costly" at the top.

ভিত্তিতে অনেক ছোট automated component test (দ্রুত, সস্তা), উপরে অল্প end-to-end test (ধীর, ব্যয়বহুল) — টেস্টের অধিকাংশ থাকা উচিত base-এ।

Ch 5 §5.1 →

Test quadrantsK2

"Q1 · technology-facing, supports the team · Q2 · business-facing, supports the team · Q3 · business-facing, critiques the product · Q4 · technology-facing, critiques the product."

Q1 tech/supports (component, integration) · Q2 business/supports (functional, BDD) · Q3 business/critiques (acceptance, exploratory, UAT) · Q4 tech/critiques (performance, security)।
⚠️ Performance testing is Q4, technology-facing — examiners love parking it in a business-facing quadrant.

Ch 5 §5.1 →

RiskK2

"Risk = likelihood × impact."

Risk = likelihood × impact — risk assessment = চিহ্নিত করা + analysis করা + mitigation ঠিক করা; testing নিজেই একটি mitigation।
⚠️ Rank by multiplication, never eyeball — A = 2×5 = 10, B = 4×3 = 12, so B is the higher risk.

Ch 5 §5.2 →

Product vs project riskK2

"Product risk — the work product may fail its users… Project risk — threats to the project itself: staffing, skills, conflicts, supplier trouble, bad estimates."

Product risk = work product ব্যবহারকারীদের কাছে ব্যর্থ হতে পারে (data leak); project risk = প্রকল্পের নিজের ওপর হুমকি (vendor দেউলিয়া, release দেরি)।

Ch 5 §5.2 →

Residual riskK2

"the risk that remains afterwards is residual risk, which must be communicated to stakeholders."

Risk-based testing-এর পরেও যে risk থেকে যায় সেটাই residual risk — stakeholder-দের কাছে জানাতেই হবে।

Ch 5 §5.2 →

Severity vs priorityK2

"Severity = technical impact ('crashes when saving'). Priority = business urgency ('must fix before the demo')."

Severity = technical impact; priority = ব্যবসায়িক তাড়া — দুটো আলাদা দিকে যেতে পারে: launch-এর আগের রাতে homepage typo = কম severity, বেশি priority।

Ch 5 §5.5 →

Defect lifecycleK2

"New → Assigned → Fixed → Confirmation test → passes → Closed"; "fails → Reopened ↺ back to Assigned." Side states: "Rejected · Duplicate · Deferred."

New → Assigned → Fixed → confirmation test → pass করলে Closed, fail করলে Reopened; পাশের state: Rejected, Duplicate, Deferred।
⚠️ "Fixed" is not the end: the confirmation test precedes closing.

Ch 5 §5.5 →

Defect reportK3

"Steps to reproduce — ordered, precise · Expected vs actual result (both!) · Environment / build under test · Severity" — plus unique ID, title, date & reporter, evidence, references.

ভালো report-এ থাকে: reproduce করা যায় এমন steps, expected এবং actual, build ID, severity — দোষারোপ নয়।
⚠️ Penalise: blame ("Sam's fault"), vagueness ("crashes sometimes"), several defects bundled in one report, missing expected result.

Ch 5 §5.5 →

Monitoring vs controlK2

"Monitoring = gather data, compare progress vs plan. Control = act on it — re-prioritise, adjust schedule, add automation. (Observe → correct.)"

Monitoring = data জোগাড় করে plan-এর সঙ্গে তুলনা; control = সেই তথ্যের ভিত্তিতে ব্যবস্থা নেওয়া (দেখা → সংশোধন)।

Ch 5 §5.3 →

ƒ Risk levelK2

risk = likelihood of the event × impact of the event — rank items by the product to decide test priority: highest risk gets tested first and most intensely. Example: A = 2×5 = 10; B = 4×3 = 12 → test B first.

Risk = event-এর likelihood × impact; গুণফল অনুযায়ী rank করে সবচেয়ে বড় risk আগে ও বেশি intense ভাবে test করা হয়।
⚠️ Severity = technical impact; priority = business urgency — they can diverge (homepage typo: low severity, high priority).

Support toolsK2

"keep test work efficient & manageable" — CI/CD, build tools, version control, incident management, spreadsheets.

Support tool মানে test-এর কাজ দক্ষ ও নিয়ন্ত্রণযোগ্য রাখে — CI/CD, build tool, version control, incident management, spreadsheet।

Non-functional testing toolsK2

"measure quality characteristics" — performance/load tools, security scanners.

Non-functional tool মানে quality characteristic মাপে — performance/load tool, security scanner।

Tool benefits & risksK2

Benefits come from automating repetitive work. Risks: "Unrealistic expectations · Underestimated time, cost, effort of introduction and ongoing maintenance · Over-reliance · Vendor dependency."

Benefit আসে পুনরাবৃত্ত কাজ automate করা থেকে; risk: অবাস্তব প্রত্যাশা, introduction ও maintenance-এর খরচ কম ভাবা, অতিরিক্ত নির্ভরতা, vendor dependency।
⚠️ A tool helps but never guarantees — it cannot replace tester skill/judgement.
