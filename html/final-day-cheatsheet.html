2 · The 7 testing principles (Ch 1)

K2

1 PresencePassing tests ≠ bug-free — testing shows the presence of defects, never their absence
2 ExhaustiveExhaustive testing is impossible → prioritise by risk & criteria
3 EarlyEarly testing (shift-left) saves time & money — req defect 1×, production 100×
4 ClusteringFew modules hold most defects → focus effort there
5 Pesticide ↗Same tests stop finding new defects → update/improve the tests
6 ContextNo one right way — safety-critical ≠ e-commerce
7 FallacyAbsence-of-errors: all bugs fixed + wrong system = still failure

3 · error → defect → failure (Ch 1)

K2

LinkDefinitionHuman?
Error ↗A human action that produces a defectYES — always a human action
Defect ↗A flaw in a work product, can cause failureno — in the product
Failure ↗Actual behaviour deviates from expected, at runtimeno — observed deviation
⚠️ Caveats: 1) a defect does not always cause a failure (code never run / inputs never trigger it) · 2) not every failure comes from a code defect — environment (hardware, radiation, config) or a wrong expected result can produce one; a wrong requirement also causes failures.

QA vs QC: QA = process-oriented, prevents defects (reviews, early design) · QC = product-oriented, detects defects (testing this build). Testing does both.

5 · Levels, types & maintenance (Ch 2)

K2

Ladder: component (isolated unit, dev + mocks) → component integration (interfaces between components) → system (whole behaviour, independent team) → acceptance (validation: user needs; often entry criterion for release; alpha = developer's site · beta = user's site).

Functional / non-functionalwhat the system does / how well it behaves (performance, usability, security, reliability)
Black-box / white-boxspec-based derivation / internal-structure-based derivation — ANY type at ANY level
Confirmation ↗ / regressionverify a specific defect is fixed / verify a change broke nothing else — regression after any change, at all levels, all SDLCs

3 maintenance triggers (scope = impact analysis): modification (enhancements, hotfixes) · migration (new platform/DB — needs data conversion testing + regression) · retirement (archiving, data migration). Shift-left = two halves: early work-product testing (reviews, static analysis) AND testers involved from the start.

6 roles: author — fixes defects afterwards · facilitator — ensures the review runs effectively · reviewer — examines the product, ideally not the author · scribe — collects defects/comments during the meeting · review leader — takes overall responsibility for the review, decides exit · manager — decides whether the review happens. One person may hold several roles.

Static analysis: tool-based, no execution. A compiler IS a static analysis tool.

7 · Risk, criteria & defects (Ch 5)

K2 (+K3 report)

Risk= likelihood × impact — rank by multiplying (2×5=10 < 4×3=12); report residual risk
Product riskthe work product may fail users (security holes, poor usability)
Project riskthe project fails (staffing, supplier, bad estimates, late release)
Entry criteriato start execution (env ready, testable build)
Exit criteriato declare done (tests run, coverage, defect thresholds) — both measurable
Severity / prioritytechnical impact / business urgency — can diverge (typo on launch eve = low sev, high pri)

Defect lifecycle:
New → Assigned → Fixed → confirmation test → passes: Closed / fails: Reopened. Side states: Rejected · Duplicate · Deferred. "Fixed" is not the end.

Good report (K3): unique ID · title · date/reporter · environment/build · steps to reproduce · expected vs actual result · severity · evidence · references.

Estimation: metrics-based (past data) vs expert-based (judgement — planning poker, Delphi).
Pyramid: many unit → fewer integration → few end-to-end. Quadrants: Q4 tech/critique = performance, security, reliability.

8 · Tools (Ch 6)

K2

6 categories: test management (test mgmt platform, defect tracker) · static analysis (compiler, linter) · test design/implementation (model-based, test-data generators) · test execution & automation (capture/replay, API runner) · non-functional (performance/load, security scanner) · support (version control, CI/CD, incident management).

⚠️ Performance tools = non-functional · Git/version control = support · compiler = static analysis. Tools help but NEVER guarantee; benefits come from automating repetition; risks = unrealistic expectations, underestimated intro + maintenance cost, over-reliance, vendor dependency. Pilot project = try it on one small contained project before rollout.

9 · TRAPS STRIP — the 8 highest-frequency distractors

read Friday 15:15

1. "All tests passed = defect-free" → principle 1 (presence, not absence).
2. "Testing = only executing code" → false (planning + static testing exist).
3. "Most bugs in a few modules" = defect clustering, NOT pesticide paradox.
4. Pesticide paradox remedy = new/modified tests, never "run them more often".
5. QA = process/prevention · QC = product/detection — don't swap.
6. Walkthrough = author-led; inspection = trained moderator ≠ author + metrics.
7. A compiler IS static analysis; performance tools = non-functional; Git = support.
8. 100% branch ⊃ 100% statement — never the reverse; coverage can't find missing functionality.
