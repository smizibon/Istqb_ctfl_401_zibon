1.1 What is testing?

K2

What testing is (and is not), how it differs from debugging, and the eight goals it can serve — one goal is always impossible.

In plain words: testing checks any work product against expectations; debugging then fixes the causes found.

📖 Memorise — the definition (essence) Software testing is the process of evaluating a work product to determine whether it satisfies requirements and to detect differences between given and expected results. Testing also includes planning, analysis, design, implementation, execution, and reporting — it is far more than executing tests.
🧠 Understand — the three contrasts you must articulate Testing vs. debugging. Testing detects failures caused by defects. Debugging finds, analyses, and removes their causes. Testing answers "is there a problem?"; debugging answers "why, and how do I fix it?" Debugging is a development activity, not a testing activity — though testers often help developers reproduce failures.

Dynamic vs. static testing. Dynamic = running the software (or any executable work product) and observing behaviour. Static = examining work products without running them (reviews, static analysis). Testing includes both.

Any work product can be tested. Requirements documents, user stories, design models, source code, test plans, even the tests themselves — all are testable.
⚠️ Traps • "Testing always requires executing code" — false (static testing exists).
• "Testers only test running software" — false (any work product).
• An option describing "finding and removing causes" is debugging, not testing.

Test objectives (1.1.2)

K2

Testing may aim to:

  • Prevent defects (e.g., by reviewing requirements)
  • Verify that requirements are fulfilled
  • Check whether the system works as expected
  • Build confidence in the level of quality
  • Find defects
  • Reduce risk (of failures in operation)
  • Provide information for stakeholders' decision-making
  • Comply with law, regulation, or standards
Exam pattern: a scenario + "which objective fits?" — e.g., "the team tested to fulfil a contractual acceptance criterion" → the compliance objective. Watch for the impossible objective: "proving there are no defects" is never valid.

সংজ্ঞা, testing-vs-debugging আর static-vs-dynamic পার্থক্য, এবং ৮টি test objective (টেস্ট উদ্দেশ্য) — যার মধ্যে একটি সবসময়ই অসম্ভব।

📖 Memorise — সংজ্ঞা (মূল কথা) Software testing হলো একটি work product (কাজের ফলাফল) মূল্যায়ন করার process, যাতে নির্ধারণ করা যায় এটি requirements পূরণ করে কি না এবং প্রদত্ত ও প্রত্যাশিত ফলাফলের মধ্যে পার্থক্য detect করা যায়। Testing-এর মধ্যে আরও রয়েছে planning, analysis, design, implementation, execution এবং reporting — অর্থাৎ এটি শুধু test execute করার চেয়ে অনেক বেশি কিছু।
🧠 Understand — যে তিনটি পার্থক্য তুমিকে বলতে পারতেই হবে Testing vs. debugging. Testing defect-এর কারণে সৃষ্ট failure শনাক্ত করে। Debugging সেই কারণগুলো খুঁজে বের করে, analysis করে এবং দূর করে। Testing-এর উত্তর: "সমস্যা আছে কি না?"; debugging-এর উত্তর: "কেন, এবং কীভাবে ঠিক করব?" Debugging একটি development activity, testing activity নয় — যদিও tester-রা প্রায়ই developer-দের failure reproduce করতে সাহায্য করেন।

Dynamic vs. static testing. Dynamic মানে software (বা যেকোনো executable work product) চালিয়ে আচরণ পর্যবেক্ষণ করা। Static মানে work product চালানো ছাড়াই পরীক্ষা করা (review, static analysis)। Testing-এর মধ্যে দুটোই পড়ে।

যেকোনো work product-ই test করা যায়। Requirements document, user story, design model, source code, test plan, এমনকি test নিজেই — সবই testable।
⚠️ Traps • "Testing always requires executing code" — ভুল (static testing বিদ্যমান)।
• "Testers only test running software" — ভুল (যেকোনো work product)।
• "finding and removing causes" বর্ণনা করা কোনো option হলো debugging, testing নয়।

Test objectives (1.1.2)

Testing-এর লক্ষ্য হতে পারে:

  • Defect প্রতিরোধ করা (যেমন requirements review-এর মাধ্যমে)
  • Verify করা যে requirements পূরণ হয়েছে
  • পরীক্ষা করা সিস্টেমটি প্রত্যাশা অনুযায়ী কাজ করে কি না
  • মানের মাত্রা নিয়ে আত্মবিশ্বাস তৈরি করা
  • Defect খুঁজে বের করা
  • risk কমানো (operation-এ failure-এর)
  • Stakeholder-দের সিদ্ধান্ত নেওয়ার জন্য তথ্য দেওয়া
  • আইন, রেগুলেশন বা standard মেনে চলা (compliance)
Exam pattern: একটি scenario + "কোন objective মানায়?" — যেমন "the team tested to fulfil a contractual acceptance criterion" → compliance objective। অসম্ভব objective-টি খেয়াল রাখো: "proving there are no defects" কখনোই বৈধ নয়।

1.2 Why testing is necessary — errors, defects, failures

K2

Why defects exist: the human mistake → product flaw → observed failure chain, its caveats, and QA vs QC.

In plain words: people make mistakes, mistakes leave flaws, flaws may (or may not) surface as failures.

The quality chain

Error (mistake)a human action that produces a defect — a developer misreads the spec and types the wrong formula
→
Defect (bug/fault)a flaw in a work product, can cause failure — the code contains the wrong interest formula
→
Failureactual behaviour deviates from expected, observed at runtime — ATM shows a wrong balance
⚠️ The caveats the exam loves 1. A defect does not always cause a failure — the wrong code may never be executed, or the inputs may never trigger it.
2. Not every failure comes from a code defect — environmental conditions (radiation, electromagnetic interference, hardware faults, wrong setup/configuration) can cause failures. And if the expected result was wrong (bad oracle), a "failure" may be observed even when the system behaves as designed.
3. A failure can also be caused by an error in any work product — a wrong requirement causes the code to faithfully implement a defect.

Root causes of errors (1.2.3)

K2

📖 Memorise — typical root causes Time pressure · human fallibility · inexperienced/inadequately trained staff · miscommunication (verbal, written, ambiguous requirements) · complexity of code/design/architecture · misunderstanding interfaces · new/unfamiliar technologies · incorrect handling of system states and conditions.
⚠️ TrapRoot-cause questions: "environmental conditions" offered as a cause of failure = correct; offered as a cause of error = wrong — an error is always a human action.

Contributions to success; QA vs. QC (1.2.1)

K2

🧠 Understand — how testing improves quality
Quality assurance (QA)Quality control (QC)
FocusProcess-oriented — "are we doing the right things right?"Product-oriented — "is this build good?"
AimPreventing defects (through reviews and early test design)Detecting and evaluating defects

In plain words: QA improves how you work so bugs never appear; QC checks the thing you built.

Testing also provides measures of quality (defect counts, coverage) and reduces risk — the earlier a defect is found, the cheaper it is to remove.
⚠️ Top trap • "Testing proves the system is correct" — false. Testing can show the presence of defects, never their absence.
• Testing alone does not ensure quality — quality is built through the whole development effort; testing gives information about quality.

Error→defect→failure চেইনটি তার সতর্কতা সহ (defect ≠ failure), error-এর root cause, এবং QA-vs-QC — testing মানের ব্যাপারে তথ্য দেয়, কখনোই প্রমাণ করে না।

The quality chain

Error (mistake)একটি মানুষের কাজ (human action) যা defect তৈরি করে — developer spec ভুল পড়ে ভুল formula টাইপ করল
→
Defect (bug/fault)work product-এর মধ্যে একটি ত্রুটি, failure ঘটাতে পারে — code-এ ভুল interest formula আছে
→
Failureপ্রকৃত আচরণ প্রত্যাশিত আচরণ থেকে সরে যায়, runtime-এ দেখা যায় — ATM ভুল balance দেখাল
⚠️ যে caveat-গুলো পরীক্ষায় বারবার আসে 1. একটি defect সবসময় failure ঘটায় না — ভুল code কখনো execute নাও হতে পারে, বা input কখনোই সেটি trigger করে না।
2. প্রতিটি failure-এর উৎস কোনো code defect নয় — পরিবেশগত শর্ত (radiation, electromagnetic interference, hardware fault, ভুল setup/configuration) failure ঘটাতে পারে। আর যদি প্রত্যাশিত ফলাফলটাই ভুল হয় (খারাপ oracle), তাহলে সিস্টেম যেমন ডিজাইন করা হয়েছে তেমনই আচরণ করলেও একটি "failure" দেখা দিতে পারে।
3. একটি failure যেকোনো work product-এর error-ও ঘটাতে পারে — ভুল requirement-এর কারণে code বিশ্বস্তভাবে একটি defect implement করে।

Root causes of errors (1.2.3)

📖 Memorise — সাধারণ root cause-গুলো সময়ের চাপ · মানুষের ভুল হওয়ার স্বভাব · অনভিজ্ঞ/অপর্যাপ্ত প্রশিক্ষণপ্রাপ্ত কর্মী · ভুল যোগাযোগ (মৌখিক, লিখিত, অস্পষ্ট requirements) · code/design/architecture-র জটিলতা · interface ভুল বোঝা · নতুন/অপরিচিত technology · সিস্টেমের state ও condition-এর ভুল হ্যান্ডলিং।
⚠️ TrapRoot cause-এর প্রশ্নে: "environmental conditions" যদি failure-এর কারণ হিসেবে দেওয়া হয় = সঠিক; কিন্তু error-এর কারণ হিসেবে দেওয়া হলে = ভুল — error সবসময়ই একটি মানুষের কাজ।

Contributions to success; QA vs. QC (1.2.1)

🧠 Understand — testing কীভাবে মান বাড়ায় Testing মান বাড়ায় defect detect ও মূল্যায়ন করার মাধ্যমে — এটাই quality control (QC), product-মুখী: "এই build কি ভালো?" — এবং review ও দেরিতে-না-করা test design-এর মাধ্যমে defect প্রতিরোধ করে — এটাই quality assurance (QA), process-মুখী: "আমরা কি সঠিক কাজগুলো সঠিকভাবে করছি?" Testing এছাড়াও মানের মাপ দেয় (defect সংখ্যা, coverage) এবং risk কমায় — defect যত আগে পাওয়া যায়, দূর করা তত সস্তা।
⚠️ Top trap • "Testing proves the system is correct" — ভুল। Testing defect-এর উপস্থিতি দেখাতে পারে, অনুপস্থিতি কখনোই নয়।
• শুধু testing করেই মান নিশ্চিত হয় না — মান গড়ে ওঠে পুরো development প্রচেষ্টা জুড়ে; testing মান সম্পর্কে তথ্য দেয়।

1.3 The Seven Testing Principles

K2

Seven rules of thumb every tester must know — the exam gives a mini-story, you name the rule.

In plain words: seven common-sense limits of testing — learn to spot each from a one-line story.

📖 Memorise + apply — scenario → principle must be instant (~half of Ch 1 marks)
PrincipleOne-line meaningExam-hook scenario
1. Presence, not absencePassing tests ≠ bug-freeTeam ships after all tests pass; users still find bugs
2. Exhaustive testing is impossibleCan't test every input combination → prioritise by risk & criteria"Test all input combinations" gets rejected
3. Early testing (shift-left)Test as early as possible in the SDLCRequirements defect costs 1×, production 100×
4. Defect clusteringFew modules hold most defects80% of bugs in 3 of 40 modules → focus effort there
5. Pesticide paradoxSame tests stop finding new defects → update/improve the testsRegression suite finds nothing new for months
6. Context-dependentNo one right way; safety-critical ≠ e-commerceE-commerce approach applied to a medical device
7. Absence-of-errors fallacyAll bugs fixed + wrong system = still failureMeets (wrong) spec perfectly; users reject it

• Pesticide paradox described as "tests wear out" → the remedy is new/modified tests, never "run them more often".
• Principles appear as K2 scenarios: read the mini-story, name the principle. Practise until the mapping is instant.

1.4 The test process

K2

The seven test activities and what each produces, plus the basis/condition/case/procedure vocabulary and traceability.

In plain words: a repeating loop of seven activities — plan, watch, analyse, design, build, run, close.

🧠 Understand — context-driven (1.4.1) There is no one universal test process — it depends on context: product, risk, stakeholders, SDLC model, team, regulation.

The seven activities + work products (1.4.2 / 1.4.3)

K1

ActivityPurposeTypical work products
Test planningDefine objectives & approachTest plan
Test monitoring & controlCompare progress vs. plan, take corrective actionTest progress reports, documented corrective actions
Test analysisIdentify test conditions (what to test) from the test basisTest conditions list
Test designCreate test cases & data, design the environmentTest cases, test data, environment design
Test implementationMake things executable: procedures, suites, environment setupTest procedures, test suites, schedules
Test executionRun tests, compare actual vs. expectedTest results, defect reports
Test completionCollect experience at milestones (release, project end)Test completion report, lessons learned

Key vocabulary — memorise exactly

📖 Memorise — the four definitions • Test basis — the body of information a test is based on (requirements, user stories, design).
• Test condition — an item/event to be tested ("interest calculation on overdue accounts").
• Test case — input + execution preconditions + expected result (the expected result is what makes it a case, not just a trial run).
• Test procedure (test script) — step-by-step instructions for executing test cases, in order.

Traceability (1.4.4)

K2

🧠 Understand — why we trace Traceability links test basis ↔ test conditions ↔ test cases ↔ results. It enables: coverage evaluation, impact analysis of changes, audits, and reporting "requirement X is tested".
⚠️ Traps • Analysis answers what to test; design answers how.
• Activities overlap and iterate — they need not be strictly sequential (especially in Agile).
• Expected results must be defined before execution — otherwise "the output looked fine" bias creeps in.

৭টি test activity তাদের work product সহ, basis/condition/case/procedure শব্দভাণ্ডার, এবং traceability কেন গুরুত্বপূর্ণ।

🧠 Understand — context-driven (1.4.1) কোনো একটি সর্বজনীন test process নেই — এটি context-এর উপর নির্ভর করে: product, risk, stakeholder, SDLC model, team, regulation।

• Test procedure (test script) — test case-গুলো ক্রমানুসারে execute করার ধাপে-ধাপে নির্দেশনা।

Traceability (1.4.4)

🧠 Understand — কেন trace করি Traceability test basis ↔ test condition ↔ test case ↔ result-কে সংযুক্ত করে। এটি সক্ষম করে: coverage evaluation, পরিবর্তনের impact analysis, audit, এবং "requirement X tested" রিপোর্ট করা।
⚠️ Traps • Analysis-এর উত্তর কী test করব; design-এর উত্তর কীভাবে।
• Activity-গুলো একে অপরকে ছাপিয়ে যায় এবং iterate হয় — কড়া ক্রমিক হওয়া জরুরি নয় (বিশেষত Agile-এ)।
• Expected result execution-এর আগেই নির্ধারণ করতে হবে — নাহলে "the output looked fine" বায়াস ঢুকে পড়ে।

What testers need to know, the five rungs of test independence, and why quality is everyone's job.

📖 Memorise — skills (1.5.1) Testing needs both professional/technical skills (test techniques, tools, standards, SDLC) and interpersonal skills (communication, critical thinking, analytical, teamwork). Domain knowledge helps; independence reduces the author's bias — "everyone tests better someone else's work".

Whole-team approach (1.5.2)

K2

🧠 Understand — the tester's role Quality is everyone's job. Testers act as coaches, catalysts, and information providers; they collaborate with business representatives on acceptance criteria and with developers on testability (e.g., test automation interfaces). Testers also promote quality thinking — asking "what if…", challenging assumptions, making quality visible.

Tester-এর skill, independence-এর ৫-স্তরের মই (ক্রমটি মনে রাখো), এবং whole-team approach — tester হলেন coach, gatekeeper নন।

Top exam traps in this chapter

The six wrong answers the exam keeps tempting you with.

In plain words: six recurring bait options — know them cold before Friday.

⚠️ All six, cold 1. "All tests passed, so the software is defect-free" → principle 1.
2. Any option implying testing = only executing code → ignores planning/static testing.
3. Scenario describes most bugs in a few modules → defect clustering, not pesticide paradox.
4. Pesticide paradox as "tests wear out" → the remedy is new/modified tests, not running them more often.
5. Independence question: "most independent" = testers from outside/3rd party; "independent team inside the organisation" is one level lower.
6. Root-cause question: "environmental conditions" as a cause of failure (correct) vs. as an error cause (an error is a human action).

6. Root cause-এর প্রশ্নে: "environmental conditions" যদি failure-এর কারণ হয় (সঠিক) বনাম error-এর কারণ হিসেবে দেওয়া হয় (error একটি মানুষের কাজ)।

Knowledge check — say it out loud, then reveal

Ten recall checks — say each answer aloud, then reveal.

In plain words: quiz yourself aloud; only then open the answer.

1. A test team runs the same regression suite for a year; lately it finds no defects. Which principle applies, and what is the correct response?
Pesticide paradox; respond by updating/improving the tests — not running them more often.
2. Name the three links in the error→defect→failure chain, and one reason a defect might never cause a failure.
Error (human act) → defect (flaw in a work product) → failure (observed deviation); the code may never be executed, or the inputs never trigger it.
3. Which activity produces test conditions, and which produces test procedures?
Test analysis → conditions; test implementation → procedures.
4. True/false: 100% branch testing of all code guarantees absence of defects.
False — testing shows the presence of defects, never their absence (principle 1).
5. A tester hired from an external test services company is what level of independence?
Level 4 — independent testers from outside the organisation.
6. Which single test objective is about prevention, and name two ways it is achieved?
Preventing defects in the work products (e.g., via requirements reviews and early test design). The other objectives — verifying requirements, checking the system works as expected, finding defects, providing information for stakeholders, reducing risk, building confidence, and compliance — are detection- or information-oriented.
7. What makes a test case a test case (which element is mandatory)?
The expected result — without it you cannot judge the actual behaviour.
8. Which principle does "reviewing requirements before coding starts" illustrate?
Early testing / shift-left (testing work products early).
9. QA or QC: "measuring defect density per release"… and "training developers in defensive coding"?
Measuring defect density = QC (product); training developers = QA (process).
10. What is the test basis, and name two traceability benefits.
The information a test is based on; benefits: coverage evaluation and change impact analysis (also audits, reporting).

১০টি recall check — প্রতিটির উত্তর জোরে বলো, তারপর reveal করো।

প্রশ্ন ১. একটি test team এক বছর ধরে একই regression suite চালাচ্ছে; সম্প্রতি এটি আর কোনো defect খুঁজে পায় না। কোন principle প্রযোজ্য, এবং সঠিক প্রতিক্রিয়া কী? উত্তর: Pesticide paradox; প্রতিক্রিয়া হলো test-গুলো update/improve করা — আরও ঘন ঘন চালানো নয়।

প্রশ্ন ২. Error→defect→failure চেইনের তিনটি সংযোগস্থলের নাম বলো, এবং একটি defect কেন কখনোই failure ঘটাতে পারে না তার একটি কারণ দাও। উত্তর: Error (মানুষের কাজ) → defect (work product-এর ত্রুটি) → failure (পর্যবেক্ষণ করা বিচ্যুতি); code সম্ভবত কখনো execute-ই হয় না, বা input কখনো সেটি trigger করে না।

প্রশ্ন ৩. কোন activity test condition তৈরি করে, আর কোনটি test procedure তৈরি করে? উত্তর: Test analysis → condition; test implementation → procedure।

প্রশ্ন ৪. সত্য/মিথ্যা: সব code-এর 100% branch testing করলে defect না থাকার নিশ্চয়তা পাওয়া যায়। উত্তর: মিথ্যা — testing defect-এর উপস্থিতি দেখায়, অনুপস্থিতি কখনোই নয় (principle 1)।

প্রশ্ন ৫. বাইরের একটি test services company থেকে নিয়োগপ্রাপ্ত একজন tester-এর independence কোন স্তরের? উত্তর: Level 4 — প্রতিষ্ঠানের বাইরের independent tester।

প্রশ্ন ৬. কোন একটি test objective প্রতিরোধ (prevention) সম্পর্কে, এবং এটি দুটি উপায়ে অর্জিত হয় — নাম করো। উত্তর: Work product-এ defect প্রতিরোধ করা (যেমন requirements review ও দেরিতে-না-করা test design-এর মাধ্যমে)। বাকি objective-গুলো — requirements verify করা, সিস্টেম প্রত্যাশা অনুযায়ী কাজ করছে কি না পরীক্ষা, defect খোঁজা, stakeholder-দের তথ্য দেওয়া, risk কমানো, আত্মবিশ্বাস তৈরি, আর compliance — সবই detection- বা information-মুখী।

প্রশ্ন ৭. কোন বিষয়টি একটি test case-কে প্রকৃত test case বানায় (কোন element বাধ্যতামূলক)? উত্তর: Expected result — এটি ছাড়া প্রকৃত আচরণ বিচার করা সম্ভব নয়।

প্রশ্ন ৮. "Reviewing requirements before coding starts" কোন principle-এর উদাহরণ? উত্তর: Early testing / shift-left (work product আগেভাগে test করা)।

প্রশ্ন ৯. QA নাকি QC: "measuring defect density per release"… এবং "training developers in defensive coding"? উত্তর: Defect density মাপা = QC (product); developer-দের প্রশিক্ষণ দেওয়া = QA (process)।

প্রশ্ন ১০. Test basis কী, এবং traceability-র দুটি সুবিধার নাম দাও। উত্তর: যে তথ্যের উপর ভিত্তি করে test করা হয়; সুবিধা: coverage evaluation এবং পরিবর্তনের impact analysis (এছাড়াও audit, reporting)।

b — examining a work product without execution = static testing, and static testing IS testing.

b — error (human act) → defect (wrong formula in code) → failure (wrong total observed).

6. Which statement about defects and failures is TRUE?

d — a defect may never be executed or triggered; a) overstates, b) and c) ignore environmental causes of failure.

7. Which of the following is a typical root cause of errors?

c — classic root causes: time pressure, human fallibility, miscommunication, complexity, unfamiliar tech.

b — passing tests ≠ defect-free.

9. Testing every possible combination of input values for a form with 10 fields, each accepting 50 values, is rejected by the test team. Which principle justifies their decision, and what is the correct alternative?

b — exhaustive testing is impossible; the alternative is risk-based prioritisation.

c — defects concentrated in few modules = defect clustering (not pesticide paradox, which is about tests wearing out).

d — pesticide paradox remedy: update/improve the tests, not run them more often.

a — the test approach must fit the product's context (safety-critical ≠ e-commerce).
